# ヤマビヨリ(Mountain Weather プロジェクト)

サービス名は **「ヤマビヨリ」**(2026-09決定)。`C:\mountain-weather` にある、Open-Meteo無料APIだけで動く登山向け天気ツール2本(`mountain_weather_mvp.py`/`mountain_weather_detail.py`)と、その2本が共有する土台モジュール`mountain_weather_core.py`(2026-09追加、単体では実行しない)。中核機能の依存は `requests` のみ(`venv/` に導入済み。`requirements.txt`にも記載)。加えて、detail.py側のオプション機能(気象庁天気図スクリーンショット・ルート天気マップPNG)が`playwright`/`Pillow`に依存する(後述、`venv/`に導入済みだがブラウザバイナリは別PCでは`playwright install`が必要)。

ヤマビヨリの3本柱:
- **探索モード**(`mountain_weather_mvp.py`) — 広く探す。75座を横断的にスコア比較し、週末の狙い目を探索する(**広域探索型**)。
- **診断モード**(`mountain_weather_detail.py`、山選択) — 深く調べる。1つの山を14日分、標高別(地上/約762m/約1458m/約3013m)・時間帯別(AM/稜線帯/PM)に詳細診断する(**深掘り型**)。
- **GPXルート診断**(`mountain_weather_detail.py`、GPXモード) — 実際の登山計画に沿って診断する。ヤマレコの登山計画書GPXから登山口・山小屋・山頂などのwaypointsを自動抽出し、地点ごとの標高に応じた気圧面で天気を評価する。

(広域探索型/深掘り型という言い方は、上記の「探索モード」「診断モード」という呼称と対応させた社内的な分類名であり、他社の登山天気サービスの名称・分類を指すものではない。)

3つとも同じデータ取得基盤(Open-Meteo、MSM(気象庁)+ECMWF IFS(全球)、14日先までの生JSONキャッシュ)を共有しており、それぞれ「何を・どの粒度で見たいか」が違うだけである。

## 予測は「覗き見」禁止 — Open DataとClaude自身の知見のみで行うこと(重要)

ヤマビヨリが実際にユーザーへ天気予測・登山向けスコアを答える(=`mountain_weather_mvp.py`/`mountain_weather_detail.py`を実行して回答を組み立てる)際、**他の気象・登山天気予報サービス(てんきとくらす・tenki.jp・Windy・SCW・Mountain-Forecast・WeatherNews・ヤマテン等)の予報結果をWeb検索・閲覧して、その場の回答に反映することは固く禁止する。** 山の天気・登山条件について聞かれたら、それらの外部サイトを見に行くのではなく、必ず`mountain_weather_mvp.py` / `mountain_weather_detail.py`を実行して回答すること。

回答の根拠にしてよいのは次の4つだけ:
1. **Open Data**: Open-Meteo経由で取得するMSM(気象庁)+ECMWF IFS(全球)の数値予報。
2. **気象庁自身の実況・予想天気図**(`fetch_jma_weather_map()`)— これは他社の予報サービスではなく気象庁のOpen Dataそのものなので、診断モードの標準フロー内での利用は禁止事項に含まれない。
3. **このSKILL.mdに蓄積された設計知見**(スコアの重み・閾値、過去の不具合修正の経緯など、後述の各セクション)。
4. **Claude自身が持つ気象・登山に関する一般知識**(天気図の読み方など定性的な補足のみ。数値予報そのものの代替にはしない)。

**この禁止は「実際に回答を生成する瞬間」の話であり、開発時に行った精度検証(後述「既知の精度傾向」など各セクションに残る、てんきとくらす・Windy・SCW・Mountain-Forecast・WeatherNewsとの比較記録)とは別物。** それらは過去にスコア式の妥当性を検証した開発ログとして、サービス名を含めてそのまま残すこと(匿名化・一般化しない)。混同して比較記録まで書き換えないよう注意。

このSkillは `C:\mountain-weather` をカレントディレクトリとして起動されている前提。もしファイルが見つからない場合は、まず `pwd` で作業ディレクトリを確認すること。

**このSKILL.mdは仕様変更のたびに更新すること。** コード側だけ直して説明を放置すると、次回このSkillを読んだ際に古い情報(山数・番号・関数名など)をそのままユーザーに答えてしまう。過去に「36座→実際は75座」「唐松岳12番→実際は38番」「`print_ridge_feel_table`という関数は実在しない」といった記載ズレが起きている。数字・関数名を書く前に、可能なら `grep`/`python -c "import ...; print(...)"` で実際のコードを確認してから書くこと。

## 気象情報の3層構造(2026-09、ユーザーとの対話で明文化)

ヤマビヨリの気象情報は「MSM + ECMWFアンサンブル + 天気図解析」を横並びの3つの情報源のように語られることがあるが、正確には**役割が違う3層構造**である。ユーザーから「この仕組みをSKILLに書いておいて」と依頼され、この節を新設した。

1. **コア(数値予報の本体、常に使われる)**: **MSM(近距離・決定論)+ ECMWF決定論(全14日)の自動マージ**。`mountain_climb_score`をはじめ、探索モード・診断モード・GPXルート診断のすべての数値はここから来る。詳細は「共通のデータ取得ロジック」節。**ここで使っているECMWFは決定論(1本のシミュレーション)であり、アンサンブルではない**。
2. **確信度の補助レイヤー(限定的)**: ECMWFの51メンバーアンサンブル(詳細は「ECMWFアンサンブル確信度スコア」節)は、①の予報を**置き換えたり作ったりしない**。「①の予報はどれくらい信頼できるか」を別枠のスコアとして出すだけの補助指標であり、しかも**detail.pyの診断モード(山を1つ選ぶ場合)のみ**。探索モード(mvp.py)・GPXルート診断には未実装(意図的、理由は同節に記載)。
3. **天気図の目視解析(条件付き・補足)**: 気象庁の実況天気図+予想天気図(+24h/+48h、詳細は「気象庁天気図スクリーンショット機能」節)をClaude Code自身が画像として読み、点予報を定性的に補足する。毎回自動ではなく、スコアが判断に迷う範囲の時やユーザーが理由を求めた時など**条件付き**(「診断モードの標準フロー」節)。カバーする期間も実況〜48時間先までで、14日間の予報全体を裏付けているわけではない。`main()`には未接続で手動呼び出し。

**まとめの言い方**: 「決定論予報(MSM+ECMWF)が本体で、その周りに確信度チェック(ECMWFアンサンブル、診断モード限定)と天気図による目視の裏付け(近距離のみ、条件付き)を部分的に足している」。「3つの情報源を横並びで使っている」という説明は不正確なので、ユーザーや第三者にヤマビヨリの仕組みを説明する際はこの3層構造で答えること。

## ファイル構成

- `mountain_weather_core.py`(2026-09追加) — mvp.py/detail.pyが共有する土台モジュール。`MOUNTAINS`リスト、気圧面/固定高度バンドの変換ロジック(`PRESSURE_LEVELS_HPA`/`pressure_level_altitude_m`/`nearest_pressure_level`/`FIXED_ALTITUDE_BANDS_M`/`ALTITUDE_BAND_HPA`/`BAND_VARS`/`WIND_SPEED_BAND_VARS`/`nearest_band`)、スコア算出ロジック(6つのpenalty関数/`wet_chill_adjustment_c`/`SCORE_WEIGHTS`/`mountain_climb_score`/`safe_avg`/`safe_avg_or_none`/`wind_chill_c`/`KMH_TO_MS`/`WIND_PEAK_WARNING_MS`)、生JSONキャッシュ層(`fetch_open_meteo`/`_cache_path`/`_load_cache`/`_save_cache`/`get_with_retry`/`CACHE_DIR`/`CACHE_TTL_SECONDS`/`OPEN_METEO_URL`)、日付/表示ヘルパー(`display_width`/`pad`/`WEEKDAY_JA`/`format_date_with_weekday`)、`PRECIP_TIMING_*`定数を1箇所で定義する。単体では実行しない(`if __name__ == "__main__"`を持たない)、mvp.py/detail.pyから`from mountain_weather_core import (...)`されるだけのモジュール。**2026-09より前はこれら全てが2ファイルへ手でコピーされていたが、この移行で単一のソースに統合した**(詳細は各セクション参照)。
- `mountain_weather_mvp.py` — 候補となる山75座を、指定期間内で登山向け総合スコア(`mountain_climb_score`、後述)が高い順にランキング表示する非対話スクリプト。Open-Meteoレスポンスのディスクキャッシュも実装済み(core.py経由)。
- `mountain_weather_detail.py` — 山を1つ対話的に選び、(1)登山向け総合スコアの日別サマリーと(2)14日分の1時間ごと詳細(雲量・風など)の2段構成で表示する。Open-Meteoレスポンスのディスクキャッシュも実装済み(core.py経由)。
- `requirements.txt` — 中核機能の依存(`requests`)を記載。オプション機能(`playwright`/`Pillow`)は別途コメントで案内(後述のオプション依存セクション参照)。
- `venv/` — Python仮想環境。実行は `./venv/Scripts/python.exe <script>.py`。
- `cache/` — 両スクリプト共通の生JSONキャッシュ置き場(後述)。同じディレクトリだが、ファイル名キーに`days`(mvp.py=15、detail.py=14)が含まれるため衝突はしない。
- `screenshots/` — detail.py の `fetch_jma_weather_map()`(後述)が保存する気象庁天気図のPNG置き場。自動プルーニングなし(手動クリーンアップ前提)。
- `maps/` — detail.py の `render_route_weather_map()`(後述、2026-09追加)が保存するルート天気マップPNG置き場。自動プルーニングなし。

mvp.py/detail.pyは**それぞれの独自機能については引き続き意図的に独立**しており(各ファイルのdocstring参照)、GPX診断・地図PNG・ECMWFアンサンブル確信度・気象庁天気図スクリーンショット・雲海検出などdetail.py固有の機能はcore.pyに含めていない。風向・実標高ベースの風速、`past_days`を使った過去日付の一回限り取得なども引き続きdetail.py側にしかない。一方で、**`MOUNTAINS`リスト・気圧面/固定バンド変換・スコア算出ロジック・生JSONキャッシュ層は2026-09にcore.pyへ統合済み**で、もう2ファイルに手でコピーされてはいない(下記の各セクションはこの統合後の状態に更新済み)。`fmt()`(ndigits=0のとき、mvp.pyは`round(val,0)`で"1234.0"、detail.pyは`round(val)`で"1234"を返す)と`wind_peak_warning_cell()`/`precip_timing_note()`(渡す引数の形が2ファイルで異なる)は、この差異ゆえに意図的に各ファイルへ残してある — 数値自体の食い違いではなく表示コードの違いなので、統合の対象外とした。core.pyを変更する場合は自動的に両スクリプトへ反映されるが、mvp.py/detail.py固有のコードを片方だけ直すと従来通り乖離するので注意。

## 使い分けの基準

2ファイルの呼び名は**「探索モード」(mountain_weather_mvp.py)/「診断モード」(mountain_weather_detail.py)** に統一している(2026-09〜、ドキュメント上の呼称のみ。コード・ファイル名は変更していない)。

- **探索モード**(`mountain_weather_mvp.py`): 「〇〇な山を探して」「どこかいい山ない?」のような広域探索の質問。
- **診断モード**(`mountain_weather_detail.py`): 「〇〇山の天気は?」「〇〇岳を詳しく/評価して」のような個別の山を深掘りする質問。
- ユーザーから「探索モードで」「診断モードで」と直接指定された場合は、上記の対応関係に沿って迷わず該当スクリプトを実行する。

## 共通のデータ取得ロジック

- モデルは `jma_msm`(気象庁、高精度だが国内・数日先まで)と `ecmwf_ifs025`(全球、フォールバック)を別々に取得し、時刻キーでマージ(MSMの値がnullならECMWFで埋める)。
- 気圧面(hPa)は標準大気式 `pressure_level_altitude_m()` で標高に変換し、`nearest_pressure_level()` で1000/2000/3000mの固定バンドに割り当てる。どの山でも同じ3バンドで比較できるようにするため。**割り当て先は925/850/700hPa**(`PRESSURE_LEVELS_HPA`に900/800hPaが無い — 落とし穴1と同様、ecmwf_ifs025がそれらの中間気圧面でnullを返すため)で、実際の標準大気高度は925hPa≈762m・850hPa≈1458m・700hPa≈3013m。つまり内部の`FIXED_ALTITUDE_BANDS_M = [1000, 2000, 3000]`はあくまで名目上のキー(mvp.py/detail.py共通のバンド識別子・スコア設計思想)で、特に「2000m帯」は実際には約1460m相当とズレが大きい(`ALTITUDE_BAND_ACTUAL_M`に実高度を保持)。
  - **mvp.py**は75山横断比較用にこの名目ラベル(1000m/2000m/3000m)をそのまま表示に使う(未変更、変更不要という判断)。
  - **detail.py**は2026-09に表示ラベルのみ実高度ベースに変更済み。`print_hourly_table()`の列見出しは`band_altitude_label()`(例:「雲量約1458m%」「風約1458m」)で実高度を直接表示し、見出し下の説明行にも対応する気圧面(925hPa≈約762m/850hPa≈約1458m/700hPa≈約3013m)を明記する。内部のdictキー(`cloud_1000m`等の行データ、`ALTITUDE_BAND_HPA`等の1000/2000/3000という数値)自体は名目値のままで変更していない(表示層のみの修正)。
  - **より2000mに近い気圧面の検討結果**: 800hPa(≈1949m)は850hPa(≈1458m)より2000mにはるかに近いが、上記の理由(ecmwf_ifs025が900/800hPaでnullを返す)で`PRESSURE_LEVELS_HPA`から意図的に除外されている。バンド自体を800hPaに差し替える場合は、ecmwf_ifs025が実際に800hPaの風速・雲量・気温でnullを返すかどうかの再検証が前提(2026-09時点では未検証・現状維持)。
- 旧式にあった"look-up"合成(ある高度から見上げた際の最大雲量の近似)は**両ファイルとも廃止済み**。現在はどちらも「稜線帯そのものの雲量」を直接使う。コード中のコメントに名残の言及があるのみ。

## スコア計算式 — mountain_weather_core.py で一元管理(2026-09〜)

両ファイルとも `mountain_climb_score()` が最終スコアを出す。**この関数と6つのpenalty関数(`thunder_penalty`/`wind_penalty`/`cloud_penalty`/`visibility_penalty`/`precip_penalty`/`temp_penalty`)、`wet_chill_adjustment_c`、`SCORE_WEIGHTS` は`mountain_weather_core.py`で一度だけ定義され、mvp.py/detail.pyの双方が`from mountain_weather_core import (...)`で読み込む**(2026-09より前は同じ式を2ファイルへ手でコピーしていたが、この移行で単一のソースに統合し、乖離のリスク自体をなくした)。同じ入力を渡せば同じスコアが返ることは自明(同じ関数を指しているため)だが、統合前は`mvp.mountain_climb_score(**x) == detail.mountain_climb_score(**x)`をランダム入力2000件で照合して一致を確認していた。スコア式を調整する場合は`mountain_weather_core.py`側を直せば両スクリプトに自動的に反映される。

- `mountain_climb_score(*, ridge_wind_ms, ridge_cloud_pct, ridge_visibility_m, chill_c, am_precip_prob, am_precip_mm, pm_cape)` — 100点から6軸の重み付け減点。生の測定値(スカラー)を渡す設計で、山の標高やバンド選択のロジックは呼び出し側(各ファイルの `main()`/データ集計関数)が担う。
  - 雷リスク30%: `thunder_penalty(cape)` — PM区間(12-17時)のCAPE最大値。300未満で0、300〜1000で0→40、1000〜2500で40→100と非線形に急増。
  - 稜線風25%: `wind_penalty(ridge_wind_ms)` — 稜線帯(8-11時)の風速(m/s)。8m/s未満で0、8〜12で0→40、12〜15で40→100(15m/s以上は満額減点)。閾値は気象庁の風の強さ階級表・登山系ガイド複数を調査して決定。
  - 稜線雲量12%: `cloud_penalty(ridge_cloud_pct)` — 稜線帯そのものの雲量(当該バンド/気圧面の生値)をそのまま使用。
  - 稜線視程8%: `visibility_penalty(ridge_visibility_m)` — Open-Meteoの`visibility`(m、稜線帯8-11時平均)を直接評価。1000m以上で0、100〜1000mで0→70、100m未満で70→100(視程0mで満額)。「1000m未満で行動に支障(道迷い・滑落リスク上昇)、100m未満でホワイトアウトに近い危険域」という登山ガイド一般の目安を採用。
    - 元の稜線雲量20%を12%(雲量)+8%(視程)に分割する形にした。理由: 雲量%と視程は相関が強い一方、雲量%は「そのバンドが曇っているか」の代理指標に過ぎず、実際に何mまで見えるかは直接測れない。視程を新設することでガス・ホワイトアウトの直接評価を追加しつつ、他の軸(雷30/風25/降水15/体感温度10)の重みは変更せず、"視界"カテゴリの既存予算内で配分し直すことで合計100%を維持。
    - **落とし穴**: `visibility` は `jma_msm`/`ecmwf_ifs025` を `models=` 指定すると常にnullで返ってくる。`freezing_level_height` と全く同じ制約(下記「既知の落とし穴」参照)。mvp.py/detail.pyとも、model指定なし(best_match)の別クエリで取得してマージしている。
    - **欠損時の扱い**: 稜線帯平均は `safe_avg` ではなく `safe_avg_or_none`(新設)を使い、データが無い日は0.0ではなくNoneを返す。0.0のまま平均に使うと「視程0m=ホワイトアウト」という最悪扱いになってしまうため(wind/cloudの0.0は逆に「無風/快晴」というベナイン方向なので同じ扱いにできない)。`visibility_penalty(None)`は0点(ペナルティなし)。
  - 降水15%: `precip_penalty(prob, mm)` — AM区間(登り)の降水確率と降水量(mm/h)を確率0.5+強度0.5で合成。
  - 体感温度10%: `temp_penalty(chill_c)` — 稜線帯の気温と風速からJAG/TI風冷指数(`wind_chill_c()`)で算出した体感温度に、`wet_chill_adjustment_c(am_precip_prob, am_precip_mm)` による「濡れ」補正を加えたものを渡す。5℃以上で0、-15℃以下で満額。
    - **濡れ補正(`wet_chill_adjustment_c`)**: AM区間の降水確率が50%以上かつ降水量が0.5mm/h以上のとき、`chill_c`から一律-3℃する(それ以外は補正なし)。低体温症は「低温+強風+濡れ」の複合要因で進行するが、`wind_chill_c()`は乾いた風冷指数のみを評価しており濡れによる悪化を捉えられないための対応。
    - 実装方針は「chill_cに事前補正をかけてから`temp_penalty`に渡す」案(temp_penalty自体のシグネチャは変えない)を採用。降水確率・降水量は既に`precip_penalty`向けに`mountain_climb_score`へ渡されている値をそのまま流用するため、呼び出し側(`main()`/`compute_day_scores()`)の変更は不要。
    - 連続的なランプではなく単純な閾値判定(ステップ関数)にしている。「-2〜3℃程度」という指示に対する簡略実装で、閾値・減点幅とも要検討・要retune。

**入力値(ridge_wind_ms等)の算出方法だけが2ファイルで異なる**(データ取得の粒度が違うため):

- **mvp.py**: 75山を同じ固定バンド(1000/2000/3000m、`nearest_band(elevation_m)`で標高に応じ選択)で横断比較するため、風速・雲量・気温はすべて固定バンドの気圧面変数(`windspeed_XXXhPa`/`cloudcover_XXXhPa`/`temperature_XXXhPa`)から取得。`window_scores_by_day()` がAM/稜線帯/PMごとに集計する。視程だけは気圧面変数が存在しないため、山の緯度経度そのものにおける単一のサーフェス値(`visibility`)を標高バンドに関係なく使う。
- **detail.py**: 選択した1山の**実標高**に最も近い気圧面(`wind_vars_for_elevation()`/`temp_var_for_elevation()`)から風速・雲量・気温を取得する。**気温は2026-09に`temperature_XXXhPa`の直接取得へ変更済み**(旧: 氷点高度(`freezing_level_height`)+標準気温減率から`estimate_temp_c()`で推定していたが、てんきとくらすとの実地比較で3〜5℃の温暖バイアスが判明したため廃止。詳細は次段落)。視程は`freezing_level_height`と同じく`fetch_visibility()`(model=None)で別途取得。`compute_day_scores()` が同じ3区間で集計する。

## 3つの評価期間(mvp.py・detail.py共通)

登山の行動全体(登り・稜線滞在・下山)をカバーする設計。「早出早着」の経験則(午後は積乱雲が発達し雷リスクが上がる)をスコアに反映する狙いで、PM区間だけ雷リスク評価に特化させている。

- AM(登り): `TRIP_START_OFFSET_HOURS`/`TRIP_DURATION_HOURS`(日の出基準。デフォルト日の出-1h〜6時間) — 降水評価に使用。
- 稜線帯滞在: `RIDGE_START_HOUR`〜`RIDGE_END_HOUR`(デフォルト8-11時、固定時刻) — 風・稜線雲量・体感温度評価に使用。
- PM(下山・対流雷リスク): `PM_START_HOUR`〜`PM_END_HOUR`(デフォルト12-17時、固定時刻) — CAPE最大値による雷リスク評価に使用。

detail.py側は、この3区間とは別に「日の出+`EARLY_START_OFFSET_HOURS`〜日の入り」の**表示用**時間帯(1時間ごとテーブル、後述)も持つ。両者は独立した概念で、たまたま開始オフセットが同じ値(-1h)なだけ。

## mountain_weather_detail.py 固有の機能

- 起動直後に `main()` が入力経路を選ばせる(2026-09追加): 「1: 山を1つ選んで診断」(既存の`MOUNTAINS`選択フロー、`main_single_mountain()`)/「2: GPX登山計画書からルート診断」(`main_gpx_route()`、後述)。非対話実行は `echo "1\n<山番号>" | python mountain_weather_detail.py` のように先頭にモード番号を追加する。
- **モード1**: `MOUNTAINS` リストを番号付きで表示し、対話入力(`input()`)で1山選択。**番号はリストの並び順に依存するので、リストを変更したら番号もずれる**(2026-09時点で75座、唐松岳は38番。番号を使う前に必ず `print_mountain_list()` の出力かリストを確認し、このSKILL.md記載の番号も含めて鵜呑みにしないこと)。

     - **列見出しは名目値(1000m/2000m/3000m)ではなく実高度で表示**(2026-09改修。`band_altitude_label()`が`ALTITUDE_BAND_ACTUAL_M`から「雲量約1458m%」「風約1458m」のようなラベルを生成)。名目ラベルとの誤差(特に850hPa帯が名目「2000m」に対し実約1458mとズレ約540m)が登山判断に無視できないため、mvp.pyの名目バンド設計はそのままに、detail.pyの表示だけ実高度化した。見出し下の説明行にも対応する気圧面(925hPa≈約762m/850hPa≈約1458m/700hPa≈約3013m)を明記。内部の行データキー(`cloud_1000m`等)自体は名目値のままなので、コードを読む際は「キー名の1000/2000/3000」と「画面表示上の実高度」が別物である点に注意。
- `print_comparison_table()` はWindy/SCWとの目視比較用の生値テーブル。`main()`には未接続で、一回限りの検証をしたい時に手動で呼ぶ用途(docstring参照)。
- 風向・気温の内部処理:
  - 稜線帯の日別スコア(`print_day_score_table`の稜線風速m/s列)には、選択した山の**実標高**に最も近い気圧面(`wind_vars_for_elevation()` → `nearest_pressure_level()`)から取得した風速・風向を使う。固定1000/2000/3000mバンド(`print_hourly_table`用)とは別軸。
  - **気温(2026-09に方式変更)**: `temp_var_for_elevation()`が返す`temperature_XXXhPa`(選択した山の実標高に最も近い気圧面、`wind_speed_var`/`cloudcover_XXXhPa`と同じ気圧面)を直接取得して使う。
    - **旧方式(廃止)**: `freezing_level_height`(氷点高度=0℃線の標高)と標準気温減率(0.65℃/100m)から`estimate_temp_c()`で山の実標高ちょうどの気温を逆算していた。「`temperature_XXXhPa`は気圧面変数なので使えない」という当初の想定に基づく設計だったが、この想定は未検証だった。
    - **変更の経緯**: ユーザーが日光白根山の予報を「てんきとくらす」(700hPa/800hPa帯の気温・風を掲載する登山向け天気サービス)と目視比較したところ、てんきとくらすの700hPa気温(9〜11℃)と、試しに直接取得した`temperature_700hPa`(9.6〜10.3℃)はほぼ一致した一方、当時の`estimate_temp_c()`の推定値は13〜15℃と3〜5℃も高く出ていた。`temperature_XXXhPa`は実際には`jma_msm`/`ecmwf_ifs025`(named model)で問題なく非null値が返ってくることが判明したため(`freezing_level_height`/`visibility`とは異なり`models=`指定の制約を受けない)、`estimate_temp_c()`とその陰にあった温暖バイアスを廃止し、mvp.pyと同じ「気圧面のtemperature_XXXhPaを直接使う」方式に統一した。
    - **トレードオフ**: `estimate_temp_c()`は山の実標高ちょうど(例: 日光白根山なら2578m)の気温を計算していたが、新方式は風速・雲量と同じ「最も近い気圧面」(日光白根山なら700hPa≈実約3013m、実標高より約435m高い)の気温になる。標高の厳密さよりも数値自体の精度(実測相当のてんきとくらすとの整合)を優先した設計判断。1000/2000/3000m帯別の気温は`print_hourly_table`にはまだ未実装。

### モード2: GPX登山計画書からのルート診断(2026-09追加)

ヤマレコの登山計画書GPXを読み込み、山頂・山小屋・峠などの主要地点(waypoints)を自動抽出して、各地点の**実標高**に応じた気圧面で雲量・風・気温・総合スコアを一覧表示する機能。`MOUNTAINS`リストの単一山選択とは別の入力経路で、既存のスコア計算・気圧面変換ロジック(`nearest_pressure_level`/`fetch_open_meteo`/`compute_day_scores`/`mountain_climb_score`等)は一切変更せず再利用している(3本目のスクリプトは作らず、detail.py内に統合)。

**`MOUNTAINS`リスト(75座)とは完全に独立**(2026-09追記): `diagnose_route()`はGPXファイルから抽出した緯度・経度・標高を直接`fetch_open_meteo()`等に渡す仕組みで、`MOUNTAINS`リストの番号や登録の有無を一切参照しない。そのため`MOUNTAINS`に含まれていない山・ルートであっても、ヤマレコの登山計画書GPXさえあれば診断・地図PNG出力(`render_route_weather_map()`、後述)の対象にできる。これは探索モード(mvp.py)・診断モードのモード1(山選択)が`MOUNTAINS`リスト掲載の75座に限定されるのとの明確な違いであり、「`MOUNTAINS`に無い山だから診断できない」と誤って案内しないよう注意すること。

- **`parse_gpx_waypoints(filepath)`**: GPXの`<trkpt>`のうち**`<name>`タグを持つ点だけ**を抽出する(名前なしの大量の点はルート補間用の位置精度点で、対象外)。`{"name", "lat", "lon", "elevation_m", "time"}`の辞書リストを、ファイル内の時系列順で返す。
  - **往路・復路の重複除去**: 周回/往復ルートで同じ地名(例:「福ちゃん荘」)が2回出現する場合、ファイル内で**最初に出現した方(往路側)のみ**を採用し、以降の同名出現は捨てる。
  - `time`はGPX計画上の予定通過時刻(UTC文字列)で、**ヤマレコの計画書で実際に設定した登山日時そのもの**(2026-09、実測2件で確認済み。当初「架空の日付」と誤解していた経緯は「GPXの`<time>`タグの意味」項を参照)。テキスト診断(`diagnose_route()`)の対象日はこれとは独立に、モード1と同じ`prompt_target_date()`(YYYY-MM-DD入力、予報範囲は`today`〜`today+FORECAST_DAYS-1`)でユーザーが指定する(GPXの計画日と異なる候補日を比較したい用途向け)。地図PNG(`render_route_weather_map()`)はこれとは別に、デフォルトでGPXの`<time>`をそのまま対象日時として使う(後述)。
  - `strip_furigana(name)`: ヤマレコの`<name>`にしばしば付く末尾の「 [かな読み]」を表示用に取り除くヘルパー(例:「上日川峠 [かみひかわとうげ]」→「上日川峠」)。
  - **GPXの`<type>`タグ(数値コード)は使っていない**: 地点種別(山頂/峠/山小屋等)を表していそうだが、ヤマレコの`ptinfo.php`ページ(コード値の意味を確認しようとしたリンク先)へのアクセスが403で拒否され、**コードの意味を検証できなかった**。憶測でマッピングすると別のGPXファイルで誤分類するリスクがあるため、`type`は一切参照していない。
- **地点の絞り込みは自動判定せず、ユーザーに選ばせる**: `print_waypoint_list()`で番号付き一覧を表示し、`prompt_waypoint_selection()`でカンマ区切り番号(例:`1,3,5`)または空Enter(全地点)を受け付ける。地名パターン(「〜荘」等)や`type`コードでの自動フィルタは採用しなかった(例: 大菩薩嶺のGPXでは「福ちゃん荘」(残したい)と「勝縁荘」(除きたい)が同じ「〜荘」パターンで名前だけでは区別できず、`type`コードも上記の理由で使えないため)。
- **`diagnose_route(waypoints, target_date)`**: 選択された各waypointについて、
  1. `nearest_pressure_level(elevation_m)`でその地点の実標高に最も近い気圧面を求める(モード1の`wind_vars_for_elevation`/`temp_var_for_elevation`と同じ関数)。
  2. その地点自身の緯度経度で`fetch_forecast(lat, lon, extra_vars=[...])`を呼ぶ(=waypointごとに個別のOpen-Meteo取得。地点ごとに緯度経度が異なるため、モード1のように1回の取得では済まない。ただしキャッシュ層は共通なので、`cache/`には地点数分のlat/lon別ファイルが作られる)。
  3. `compute_day_scores()`(無変更)で対象日の`mountain_climb_score`を算出し、`print_waypoint_table()`が地点名・標高・使用気圧面・スコア内訳(稜線風速/稜線雲量/CAPE/体感温度)に続けて、日の出〜日の入りの時間帯別(雲量%・風・気温)テーブルを地点ごとに表示。
  4. 全地点分の表示が終わった後、その日のスコアで**ルート内ランキング**(降順)を1行ずつ表示する(「このルート上でどこが一番狙い目か」の判断補助。既存スコア関数をそのまま複数地点に適用しているだけで、新しい評価式は増やしていない)。
- **標高差と気圧面の分化 — 2ルートで実証済み**: `diagnose_route()`は各waypointを`nearest_pressure_level()`で925/850/700hPaのいずれかに丸めるため、**選んだ地点群がどの気圧面帯に収まるかでルート診断の見え方が大きく変わる**。実測で確認した2ケース:
  - **大菩薩嶺**(標高1584〜2057m、標高差470m、水平距離最大約2km): 全11地点が同じ850hPa(実高度≈1458m)に丸められた。850/700hPaの境界(実高度≈2235m)にどの地点も届かないため。加えてこの距離では`jma_msm`(≈5km格子)・`ecmwf_ifs025`(≈25km格子)とも同じグリッドセルに落ち、`cloudcover_850hPa`の生値が地点間でビット単位で完全一致することを確認(バグではなく、気圧面の量子化とモデル解像度の組み合わせによる制約)。
  - **唐松岳**(標高1837〜2694m、標高差857m、八方池山荘〜唐松岳山頂): 850/700hPaの境界(実高度≈2235m)を「下の樺」(2148m)と「扇雪渓」(2312m)の間でまたいだため、8地点が850hPa・700hPaの2グループに分かれた。実際に9時時点で**気温差約10℃(19.7℃ vs 9.7℃)・風速差約7.5m/s(1.1m/s vs 8.6m/s)**という明確な差が確認でき、ルート内スコアも850hPa側89.4・700hPa側88.1と分かれた。
  - **結論**: `diagnose_route()`は、選んだ地点群が925/850/700hPaの気圧面境界(実高度≈1458m/≈2235m/≈3013m)を**またぐ**標高差の大きいルートでこそ真価を発揮する。境界内に収まる(=標高差の小さい)ルートでは地点ごとに計算自体は正しく行われているが、数値上の差は出ない。
  - **目安**: 標高差が概ね800m前後あれば境界をまたぐ可能性が高い(境界間隔が約540〜1555m のため)。事前に見積もりたい場合は、ルートの最低標高・最高標高それぞれに`nearest_pressure_level()`を適用し、同じ値が返るかどうかを確認すればよい。
  - **自動注記(2026-09追加)**: `diagnose_route()`は表示の最後に、選択した地点が全て同じ気圧面に丸められていた場合(waypoint数2以上かつ使用hPaの種類が1つ)、「※選択した◯地点はすべて同じ気圧面(◯hPa≈約◯m)に丸められたため、表示値が同一になっています(...バグではありません...)」という注記を自動表示する。ユーザーが結果を見て誤ってバグと判断しないための補助であり、判定ロジック自体(`nearest_pressure_level`等)には手を入れていない。

### ルート天気マップPNG機能(detail.py、オプション、2026-09追加)

`render_route_weather_map(waypoints, target_date, start_time="05:00", out_dir=MAPS_DIR)` — 選択したGPX waypointsに、国土地理院(GSI)タイル地図を背景に天気アイコン(晴れ/曇り/雨)を配置したPNGを1枚生成する。SNS投稿等で「行動予定に沿った」天気の見通しを一目で伝えるための機能。`main_gpx_route()`の`diagnose_route()`呼び出し直後に「地図PNGを生成しますか? (y/N)」の追加プロンプトとして接続済み(y以外はスキップ、GPX診断自体には影響しない)。`diagnose_route()`と全く同じ per-waypoint fetch(`fetch_waypoint_hourly()`、2026-09にdiagnose_routeから抽出・共通化)を使うため、地図上の気温・アイコンはテキスト診断の数値と一致する。

- **依存**: `Pillow`(`venv/`に導入済み、`pip install Pillow`)。中核機能(`requests`のみ)とは別の追加依存で、`fetch_jma_weather_map()`のPlaywrightと同じ扱い(関数内で遅延import、モジュール先頭ではimportしない)。matplotlib+contextilyは検討したが不採用(下記参照)。
- **地図タイル実装方式 — matplotlib+contextily不採用、requests+Pillowで自前実装**: contextilyはrasterio(GDAL依存)等の重い地理空間スタックを追加で引き込み、Windows環境でのインストール失敗リスクが高い。GSIタイルは単なるXYZ形式のPNG画像なので、既存依存の`requests`でタイルをダウンロードし、`Pillow`で画像として合成・図形描画するだけで十分と判断し、そちらを採用した。
- **GSIタイルの利用規約(2026-09確認、https://maps.gsi.go.jp/development/ichiran.html )**: 「地理院タイルをウェブサイトやソフトウェア、アプリケーション上で**リアルタイムに読み込んで**利用する場合」は申請不要だが、**タイルをダウンロードして静的PNGとして保存・再配布する行為(=この機能そのもの)はこの適用除外に当てはまらず**、「基本測量成果となっているタイルを利用する際には、測量法に基づく申請が必要な場合があります」との記載がある(標準地図/淡色地図は基本測量成果ベース)。これはユーザーに提示済みの既知のグレーゾーンで、**個人のSNS投稿程度の小規模利用と割り切ってGSIタイルのまま実装する**選択をユーザーが明示的に行った(代替案として提示したOpenStreetMapタイルへの切り替え、背景地図なしのルート図のみ、は不採用)。大量配布・商用利用等に用途が広がる場合は、この判断を鵜呑みにせずGSIへの申請要否を再検討すること。出典表記(`GSI_TILE_ATTRIBUTION`、「地図:地理院タイル(国土地理院)」+ 一覧ページURL)は生成する全画像に描画済み。
- **使用タイル**: 淡色地図(`https://cyberjapandata.gsi.go.jp/xyz/pale/{z}/{x}/{y}.png`)。標準地図より彩度・情報量が控えめで、自前で重ねるアイコン・ラベルとの視認性の衝突が少ないため選択。タイル自体は内容が変わらない静的画像なので、Open-Meteo予報キャッシュ(3時間TTL)とは別に`cache/gsi_tiles/`へ**無期限キャッシュ**する(同じズーム・タイル座標は二度とGSIに取りに行かない)。
- **アイコン判定(`pick_weather_icon(cloud_pct, precip_prob, precip_mm)`)**: 晴れ/曇り/雨の3種類。
  - 雨: `precip_prob>=50%` かつ `precip_mm>=0.5mm/h` — `wet_chill_adjustment_c()`が使っているのと**全く同じ**「濡れ」閾値をそのまま流用(ユーザー要求の「既存の閾値ロジックを流用」に対応する部分)。
  - 曇り: `cloud_pct>=85%`(JMAの「曇り」定義=雲量9-10/10割)。こちらは`cloud_penalty()`自体には元々ブレークポイントが無い(生の%を線形減点に使うだけ)ため、**このコードベースには存在しなかった新規の閾値**(JMA基準を採用)。晴れ/曇り/雨の判定を欲張って混ぜず、この点はユーザーへの報告で明記した。
  - **唐松岳での実測での注意点**: 2日先9時台に降水確率が59〜84%まで上がっていたが`precip_mm`が全時刻0.0だったため、9地点とも「晴れ」判定になった(閾値ロジックの仕様通りで、バグではない)。降水確率だけを見た印象と表示アイコンが食い違って見えることがある点は、SNS投稿前に一度ユーザー自身の目でも点予報テーブル(`print_waypoint_table`)を確認することを推奨。
- **GPXの`<time>`タグの意味(2026-09、当初の誤解を実測で修正)**: 当初このプロジェクトは「ヤマレコの`<time>`は計画作成時に標準コースタイムから自動算出された架空の日付・時刻で、実際に登る日を表さない」という前提で実装していたが、ユーザーに実際の登山計画書2件(唐松岳:GPX取得日の翌日09:00 JST出発、大菩薩嶺:GPX取得日から見て過去の日付)を確認してもらった結果、**`<time>`は計画書で実際に設定した登山日時そのもの**であることが確認された。この前提修正に伴い、`compute_arrival_times()`と`resolve_route_target_date()`(いずれも新設/全面改修、旧実装は破棄)は以下の方針で動く。
- **到達予想時刻(`compute_arrival_times(waypoints_to_plot, all_waypoints=None, start_time_str=None)`)**: `start_time_str`省略時(デフォルト)は各地点の`<time>`(UTC)を`_gpx_time_to_local()`でAsia/Tokyoのローカル時刻に変換し、**そのまま**到達予想時刻として使う(=計画書の日時を信頼する)。`start_time_str`(例:`"07:00"`)を渡した場合のみ、出発点(`all_waypoints`の中で最も早い`<time>`、通常は登山口)の**日付はそのまま**・時刻だけをその値に差し替え、地点間の`<time>`差分(標準コースタイム)を足し込んで各地点の到達予想時刻を再計算する(「予定より遅い/早い出発時刻に変わったが、登る日自体は計画通り」というケース用)。
  - 起点(「出発点」)は常に`all_waypoints`(GPX全体、ファイル順)の中で最も早い`<time>`。**地図に表示する地点(`waypoints_to_plot`)がユーザーの選択で登山口を除外していても、起点はGPX全体の出発点のまま**になるよう、`render_route_weather_map()`は選択済みサブセットと全waypoints両方を渡す(呼び出し側`main_gpx_route()`が`all_waypoints=waypoints`を明示的に渡す)。
  - `<time>`が無いwaypointは到達予想時刻なし(`?:--`表示)となり、アイコン選択は他地点の到達予想時刻の最速値(無ければ`"12:00"`)にフォールバックする(`_closest_hour_row()`)。
- **対象日の決定と過去日付の警告(`resolve_route_target_date(all_waypoints)`)**: 地図の対象日は常にGPX出発点の`<time>`の日付(ローカル日付)。この日付が既に過去(今日より前)、または予報範囲(`今日〜今日+FORECAST_DAYS-1`)より先の場合、`fetch_open_meteo`は黙って空データを返す(Open-Meteoの予報APIはpast_daysを指定しない限り「今日」起点でしか取れないため、過去日付を指定してもエラーにはならずヒットなしになるだけ)ので、これを個別waypointの「データなし」トリクルとして出す代わりに、`render_route_weather_map()`の入口で明確な日本語メッセージ1本を出し、地図生成自体をスキップする(`None`を返す、例外は投げない)。過去日付の典型例:計画から実行日がずれ、GPXを登山日に合わせて再エクスポートしないまま使った場合。
  - `diagnose_route()`のテキスト診断は引き続き`prompt_target_date()`で**任意の対象日**を選べる(GPXの日付とは独立。計画とは違う候補日を比較したい用途向け)。そのため同じ実行内でテキスト診断と地図とで対象日が異なる場合がある(地図は`start_time`を明示的に上書きしない限りGPXの日付固定)。
  - 生成画像の左上に「対象日: YYYY-MM-DD(曜日)」ラベルを描画し、どの日を見ているかを一目で分かるようにしている。
- **ズームレベル自動調整・間引き表示の検討結果**: 「間引き」(一部地点を非表示にする)は採用せず、**ズーム自動調整+ラベルの動的オフセット配置**で対応した。
  - `_auto_zoom()`: 選択地点のbounding boxが`MAP_MAX_CANVAS_PX`(2000px、2026-09に1600→2000へ引き上げ。理由は後述)に収まる最も詳細なズーム(12〜17)を選ぶ。距離が近いクラスタ(大菩薩嶺のような11地点密集ルート)ほど自動的に高ズーム(=地点間のpx間隔が広い)になる。
    - **複数日ルートでの引き上げ(2026-09)**: 槍ヶ岳(上高地〜槍ヶ岳、約10km)のような長距離・複数日ルートでは、ルート全体を収めるために選ばれるズームが低くなり(実測でズーム13)、槍ヶ岳山頂周辺の密集クラスタ(槍ヶ岳/槍ヶ岳山荘/殺生小屋/天狗原分岐/槍沢大曲り/ババ平)のラベルが重なって見づらいとユーザーから指摘を受けた。`MAP_MAX_CANVAS_PX`を1600→2000pxに引き上げてズーム13→14相当まで上げることで解消を確認(唐松岳・谷川岳のような1日ルートでは元々もっと高いズームが選ばれているため影響なし)。**根本的なトレードオフとして残る点**: 全体を1枚に収める設計上、ルート全長と密集クラスタの実距離の比が大きいほど(例: 10kmのルート中に500m圏内の密集クラスタがある)、キャンバスサイズをどれだけ上げても両立に限界がある。大菩薩嶺クラスの密集ルート(全長も短い)は問題にならないが、槍ヶ岳のような「長い往復+山頂密集」の組み合わせでは今後も要注意。
  - `_place_label_box()`: アイコン自体は常に正確な地理座標に固定表示し、ラベル(地点名/時刻/気温)だけを8方向×2段階(近距離リング/遠距離リング、計16候補)のオフセット候補から、**全地点のアイコン footprint(自分自身も含む)+ 既に配置済みの他ラベル**と重ならない位置へ貪欲法で配置する。全候補が埋まっている密集時は最初の候補にフォールバック(=多少の重なりを許容。汎用レイアウトソルバーは導入していない)。ラベルがアイコンの真上以外にずれた場合は細い引き出し線(leader line)で対応するアイコンと結ぶ。
    - **不具合修正1(2026-09)**: 当初の実装は障害物リストに「既に配置したラベルの箱」しか入れておらず、**隣接地点のアイコン自体は障害物として扱っていなかった**ため、密集クラスタ(唐松岳の八方池山荘〜第三ケルン間、隣接地点間隔28〜46px)でラベルが隣のアイコンに重なって視認性が悪いとユーザーから指摘を受けた。修正: 描画前に全地点のアイコン矩形をあらかじめ算出し、各地点のラベル配置時に障害物として渡すようにした(`render_route_weather_map()`内、`icon_boxes`/`label_boxes`)。`_place_label_box()`/`_draw_label()`は障害物リストを直接mutateせず`(bx0,by0,bx1,by1)`を返す設計に変更し、呼び出し側が明示的に`label_boxes`へ追加する。
    - **不具合修正2(2026-09、修正1の直後に発覚)**: 修正1では「自分自身のアイコンを除く全アイコン矩形」を障害物としていたため、**太陽アイコン(晴れ)の光線が自分自身のラベルと重なる**問題が残っていた(修正1のスクリーンショットをユーザーが確認して指摘)。原因は2点: (a) 自分のアイコンをわざと障害物から除外していた、(b) アイコンの障害物矩形のマージンが`ICON_RADIUS_PX+4`(円本体基準)で、太陽アイコンの光線が`ICON_RADIUS_PX+8`まで伸びることを考慮していなかった。修正: `ICON_VISUAL_RADIUS_PX = ICON_RADIUS_PX + 8`(光線の先端まで)を新設してマージンをこちらに統一し、自分自身のアイコンも障害物に含めるようにした。あわせて`_place_label_box()`の候補オフセットも、矩形重なり判定は「いずれか1軸が完全に分離していれば重ならない」という性質を使い、**縦方向|dy|=44px(近距離)/74px(遠距離)なら自分自身のアイコン(半径21px+ラベル半高17px+余裕)を軸分離だけで確実に回避できる**よう再設計した(横方向は|dx|=85px/130px)。`MAP_CROP_MARGIN_PX`も130→190pxに拡大(オフセット候補が大きくなった分、画像端でラベルが切れないように)。
    - **唐松岳(8/9地点選択)で修正確認済み**: 密集クラスタ(八方池山荘/石神井ケルン/第二ケルン/八方ケルン/第三ケルン、隣接間隔28〜46px)を拡大して目視確認し、全5地点のラベルがアイコン(自分自身の光線も含む)・他ラベルと重ならず配置されることを確認。大菩薩嶺のような11地点ルートは未実測(GPXファイル未入手)だが、同じ仕組みで対応する設計。
- **登山コースのポリライン表示(`_draw_route_line()`、2026-09追加)**: `parse_gpx_track_points(filepath)` がGPXの**全`<trkpt>`**(名前の有無を問わない、`parse_gpx_waypoints()`とは別関数)の緯度経度をファイル順で返し、`render_route_weather_map(..., track_points=...)` がこれをピンク色(`ROUTE_LINE_COLOR`、白いハロー付きで淡色地図の等高線に負けないようにしている)のポリラインとして描画する。名前付きwaypoint同士を直線で結ぶのではなく実際のGPXトラック点を使うことで、スイッチバック等の実際の登山道の形状に沿った線になる。アイコン・ラベルより先に(=下のレイヤーとして)描画するため、線が文字を隠すことはない。`main_gpx_route()`は選択したGPXファイルから`parse_gpx_track_points()`を呼んで渡す。`track_points`省略時は線を描画しない(GPXファイル由来でない手組みのwaypointsリストにも対応するため)。
- **複数日にまたがる山行(2026-09追加)**: 槍ヶ岳(上高地〜槍沢〜槍ヶ岳、同じ登山道を戻る3日間の行程)で実証済み。
  - `parse_gpx_waypoints(filepath, dedupe=False)` — 従来の`dedupe=True`(デフォルト)は同名地点の最初の出現(往路)だけを残すが、`dedupe=False`は**全ての出現**(往路・復路、それぞれ別の`<time>`)を保持する。往復とも同じ座標を通る山小屋・分岐点は、往路(day1/2)と復路(day3、同じ登山道を1日で全部戻るような行程もある)とで別々の日時のエントリとして両方残る。テキスト診断(`diagnose_route()`、「一地点につき1行」という設計)は`dedupe=True`のまま変更していない。
  - `main_gpx_route()`は地図生成時のみ、選択された地点名の集合でフィルタした`dedupe=False`の全訪問リストを`render_route_weather_map()`に渡す(地図専用、テキスト診断には影響しない)。
  - `compute_arrival_times()`は`wp["name"]`ではなく**`id(wp)`をキー**にするよう変更(同名地点が複数エントリある場合、名前キーだと後の訪問が前の訪問を上書きしてしまうため)。
  - 対象日は`resolve_route_target_date()`(ルート全体で1つの日付)をもう使わず、`render_route_weather_map()`内で**地点(=訪問)ごとに個別の到達予定日**を解決・予報範囲チェックする(`_forecast_date_status()`、`resolve_route_target_date()`と判定ロジックを共有)。ある訪問だけ過去/範囲外でも、その訪問だけ除外して他は描画を続ける(以前は「ルート全体で1つでも範囲外なら地図全体を生成しない」という設計だったが、複数日にまたがる行程では日によって範囲外/範囲内が分かれうるため)。
  - **同じ座標に複数アイコンが乗る問題への対応(`_spread_duplicate_points()`)**: 往路・復路で同じ地点(=同じ緯度経度)を訪れる場合、アイコンをそのまま描画すると完全に重なってしまう。実際の座標(以下「真の地点」)を中心に、各訪問のアイコンを小さな環状オフセット(半径 `2*ICON_VISUAL_RADIUS_PX+6` ≈48px、太陽アイコンの光線同士が重ならない距離)でずらし、真の地点には小さな灰色の点(アンカー)を打って、各アイコンとの間を細い線で結ぶ。ラベルの重なり回避(`_place_label_box()`)は、ずらした後のアイコン位置を基準に動作するため、既存の仕組みがそのまま使える。
  - ラベルは複数日にまたがる場合、時刻の前に日付(`M/D`)を付ける(例:「9/10 10:31」)。地図左上の「対象日」表示も単一日付ではなく範囲表示(例:「対象日: 2026-09-09〜2026-09-10」)になる。判定は描画対象点の到達日の集合が2種類以上かどうか(`multi_day`変数)。
  - **実測で見つけたバグ(2026-09)**: `_spread_duplicate_points()`初版のオフセット半径(30px)は「オフセット先アイコン1個分の光線半径(`ICON_VISUAL_RADIUS_PX`=21px)」を基準に決めていたが、グループの最初のメンバーは常にオフセット0(真の座標そのまま)に置かれるため、実際に必要なクリアランスは**2個分**(42px)+余裕。テスト画像(ババ平の往復2訪問)で光線同士が接触しているのを目視で発見し、半径を`2*ICON_VISUAL_RADIUS_PX+6`(48px)に修正。
  - **`diagnose_route_by_visit_date(waypoints_to_plot, all_waypoints=None)`(2026-09追加)**: 地図(`render_route_weather_map()`)だけでなく、**テキスト診断でも複数日ルートを見たい**というユーザー要望に対応。`diagnose_route()`自体は改修せず(1つの`target_date`しか扱えないまま)、`compute_arrival_times()`で各訪問(`waypoints_to_plot`の各要素、`dedupe=False`前提)の実際の到達日を求め、日付ごとにグループ化して`diagnose_route(その日の地点群, その日の日付)`を日付昇順に呼び出すだけの薄いラッパー。地図と同じ`dedupe=False`の全訪問リスト(名前でフィルタ済み)を渡す使い方を想定。`main()`には未接続(手動呼び出し用)。槍ヶ岳3日間ルート(主要11地点、往復含む17訪問)で実証済み: 2026-09-08(上高地→槍沢ロッヂ、スコア77.7均一)/2026-09-09(ババ平・槍沢大曲りはスコア85.1、その先の槍沢・天狗原分岐〜槍ヶ岳は稜線風速16.1m/sでスコア61.3に低下)/2026-09-10(復路、スコア69.2〜73.1)と、日ごとの傾向差が正しく分かれて出力されることを確認。
- **保存先・ファイル名**: `maps/route_weather_<target_date_or_range>_<HHMMSS>.png`(生成時刻はローカル時刻)。複数日にまたがる場合は`<最初の日付>_<最後の日付>`。自動プルーニングなし。

## 雲海・快晴チャンス検出(detail.py、診断モードのみ、2026-09追加)

ヤマビヨリ当初のコンセプト「映え写真につながる晴れ間を見つける」(麓は雨でも山頂は晴れ/1000m・3000m帯は曇りでも2000m帯だけ晴れる逆転層/雲海のチャンス)を、まだ何もカバーしていなかったことにユーザーとの対話で気づき対応した機能。`main_single_mountain()`の出力に自動で追加される(GPXルート診断には未接続)。

- **3つの言い回しは同じ現象**: 「麓は雨でも山頂晴れ」「2000m帯だけ晴れ(逆転層)」「雲海」は、突き詰めると**「自分がいる高さは晴れているが、それより下のどこかに厚い雲がある」という1つのパターン**に集約される。そのため個別の検出ロジックを3つ作らず、`detect_cloud_sea_opportunity(forecast, summit_hpa)`という1つの関数でまとめて判定する。
- **新規API呼び出しなし**: 判定に使う変数(地表`cloudcover`、固定3バンドの雲量`BAND_VARS`、固定3バンドの湿度`HUMIDITY_VARS`、山の実標高バンドの雲量)は、**通常の`fetch_forecast()`が毎回すでに取得しているもの**をそのまま使う。特に`HUMIDITY_VARS`(気圧面湿度)は、「死んでいるデータ」として前回のセッションでユーザーと一緒に特定した変数(`rh_2000m`という1カラムに部分的に格納されるだけで、どの表示にも使われていなかった)で、この機能で初めて「その帯が本当に飽和しているかの裏付け」という当初の設計意図通りに使われる。
- **判定条件**: `CLOUD_SEA_CLEAR_MAX_PCT`(30%)以下の山自身の帯 + `CLOUD_SEA_DECK_MIN_PCT`(80%)以上の、山より低いいずれかの帯(地表、または固定1000/2000/3000m帯のうち山の実標高より意味のある差(100m超)で低いもの)。湿度は裏付けとして表示するのみで、必須条件にはしていない(雲量%と湿度%が必ずしも同時に閾値を超えるとは限らず、両方を必須にすると本物の雲海を取りこぼすと判断)。
- **日の出前後に限定**(`CLOUD_SEA_DAWN_START_OFFSET_HOURS`=-0.5、`CLOUD_SEA_DAWN_WINDOW_HOURS`=2.0): 雲海は夜間放射冷却で谷に溜まった湿った空気が作る現象で、日中は混合されて崩れやすいため、「晴れの上に雲がある」状態が一日中続く時間帯全部を拾うと、本来の"雲海"らしい写真映えするタイミングとは違うものまで拾ってしまう。
- **どの帯を報告するか(実装時の発見)**: 当初は「該当する帯のうち最も低い帯(=地表に近いほど"海"らしい)」を報告する設計だったが、実際の複数山のデータで検証したところ、**地表(cloudcover)が該当する場合はほぼ必ず地表が選ばれてしまい、固定バンドの湿度が一度も使われない**ことが判明した(谷川岳9/5 05時の実測: 地表雲量100%なのに925hPa帯(実高度762m)はわずか24% — 雲海が762m未満の浅い層に収まっており、追跡している固定バンドには届いていなかった)。「死んでいるデータを活用する」という目的に反するため、**「山頂に最も近い(=最も低くない)該当バンド」を優先し、どの固定バンドも該当しない時だけ地表にフォールバック**する順序に変更した。これにより、雲海が固定バンドに届くほど厚い/高い場合は湿度の裏付けが表示され、浅い谷霧のような場合は地表判定(湿度なし)になる、という使い分けが自然に働く。
- **出力**: `print_cloud_sea_opportunities()`。該当なしの場合は何も表示しない(「見つかりませんでした」的なノイズを出さない — ほとんどの山・ほとんどの日は該当せず、それ自体は特筆すべきことではないため)。
- **検証**: 75山のうち20山を対象に実行し、谷川岳・八ヶ岳・横岳等で複数のヒットを確認(いずれも2026-09-05早朝、地表雲量100%・稜線雲量0〜9%という典型的な雲海条件)。

## ECMWFアンサンブル確信度スコア(detail.py、診断モードのみ、2026-09追加)

`mountain_climb_score`自体は変更せず(MSM・ECMWFとも決定論1本のまま)、**ECMWF側の予報にだけ**、別軸の指標として「確信度」を追加した機能。`main_single_mountain()`(モード1、山を1つ選ぶ診断)の出力末尾に自動で付く(GPXルート診断には未接続)。

- **データソース**: Open-MeteoのEnsemble API(`https://ensemble-api.open-meteo.com/v1/ensemble`、`models=ecmwf_ifs025`)。ECMWFのアンサンブル予報(摂動メンバー50本 + 摂動なしのコントロールラン1本 = **51本**)を返す。レスポンスの`hourly`には、リクエストした変数名そのまま(コントロールラン)に加え、`<変数名>_member01`〜`<変数名>_member50`のキーが入る(2026-09実装時にレスポンス実物で確認済み。気圧面変数(`cloudcover_850hPa`等)にも対応していることを確認済み)。
- **`fetch_ensemble(lat, lon, hourly, days, force_refresh=False)`**: `fetch_open_meteo()`とは**意図的に完全独立**(指示の「MSM取得部分とは独立させる」に対応)。キャッシュも別ファイル(`cache/ensemble_ecmwf_ifs025_{lat}_{lon}_{days}d.json`、`_cache_path()`とは別の`_ensemble_cache_path()`)。決定論パイプラインの`ecmwf_ifs025`キャッシュと同じ命名にすると`_memberNN`キーの有無で衝突するため、ファイル名プレフィックスを`ensemble_`で分けている。TTLは既存と同じ`CACHE_TTL_SECONDS`(3時間)。
- **MSM側は対象外(意図的な設計)**: 気象庁の公式アンサンブル(MEPS)は気象業務支援センター経由の有償配信+GRIB2デコードが必要なため未対応。近未来(MSMがカバーする〜39時間)は引き続き決定論のみ。
- **確信度スコアの算出(いずれも0〜100、指示通りの仮しきい値。実測比較での再調整が今後の課題)**:
  - `cloudcover_confidence(std_pct)`: メンバー間の雲量標準偏差(pt)。0〜40ptを100〜0に線形マッピング。
  - `precip_confidence(wet_fraction)`: 降水量`ENSEMBLE_PRECIP_WET_THRESHOLD_MM`(0.1mm/h、`precip_penalty`等の「濡れ」閾値0.5mm/hより厳しめ。メンバーごとのYes/No判定はより少量から反応させる意図)以上だったメンバーの割合。0.5(五分五分)から離れるほど高スコア(`|割合-0.5|*200`)。
  - `temp_confidence(p10_p90_width_c)`: メンバー間気温の10-90パーセンタイル幅(℃、`_percentile()`で線形補間、標準ライブラリの`statistics`モジュールのみ使用・新規依存追加なし)。0〜8℃を100〜0に線形マッピング。
  - `combine_confidence()`: 3つを**単純平均**(指示にある「重み付き平均」は未実装。実データでの比較材料が無いため、まずは等重みからスタートという判断)。
- **対象期間の判定(`CONFIDENCE_MIN_DAYS_OUT = 2`)**: 今日から2日先(=day2、明日の翌日)以降のみ確信度を出す。MSMの約39時間という守備範囲が「今日」と「明日の午前」にかかりうるため、決定論パイプラインのマージ後(どの時刻がMSM由来かECMWF由来かを個別に追跡していない)からは正確な切り分けができない。保守的に日0・日1を丸ごとスキップする簡略化として実装(コード内コメントに明記)。
- **稜線帯(8-11時)ウィンドウ限定**: `mountain_climb_score`の稜線雲量・体感温度が使っているのと同じ時間帯(`RIDGE_START_HOUR`〜`RIDGE_END_HOUR`)だけを対象に確信度を平均する。スコアの入力と同じ時間帯の"ブレ"を見ている、という対応関係を保つため。
- **「予報」ラベル(晴れ/曇り/雨)**: `compute_day_scores()`(mvp.py/detail.py共通の決定論スコア関数)は一切変更せず、代わりにアンサンブル自身のコントロールラン雲量・`wet_fraction*100`(降水確率の代用)・メンバー平均降水量を`pick_weather_icon()`(GPX地図機能で新設した晴れ/曇り/雨判定、既存のまま流用)に渡してラベルを作る。確信度の数値と同じデータソースから一貫して作っているので、「予報」ラベルと「確信度」が別々の入力から来て食い違う、という事態を避けている。
- **出力例**(`print_ensemble_confidence_table()`):
  ```
  === 唐松岳(2696m) ECMWFアンサンブル確信度(2日先以降、稜線帯8-11時、51メンバー) ===
  (参考値: mountain_climb_scoreには含まれていません。予報のブレの大きさの目安です)

  日付              予報    確信度  雲量/降水/気温内訳
  2026-09-03(木)    雨      76      59/85/84
  2026-09-04(金)    雨      67      39/95/66
  ```
- **mvp.py(探索モード)には未実装**: 指示で「検討し、必要なら追加する」とされていた判断ポイント。mvp.pyは75山×3モデルを毎回叩く設計(「生JSONキャッシュ層」参照)で、コールドキャッシュ時は数分かかる。ここにさらに51メンバー分のアンサンブル取得を75山分載せると、広域比較という探索モードの本来の役割(速さ)を損なうと判断し、見送った。detail.pyの単一山深掘りモードでのみ提供する。
- **`mountain_climb_score`への不介入**: この機能はスコアの重み・入力を一切変更していない。確信度は既存スコア表(`print_day_score_table`)とは別の独立したテーブルとして追加表示されるのみで、「確信度が低いからスコアを割り引く」といった合成はしていない(指示のスコープ外、読み手が両方を見て判断する設計)。

## 気象庁天気図スクリーンショット機能(detail.py、オプション、2026-09追加)

`fetch_jma_weather_map(out_dir=SCREENSHOT_DIR)` — 気象庁の天気図ページ(https://www.jma.go.jp/bosai/weather_map/ )をPlaywrightでレンダリングし、天気図の`<img>`要素だけを切り出してスクリーンショット保存する。Open-Meteoの予報パイプラインとは完全に別系統(スコア計算には使わない、目視で実況天気図を確認するための補助機能)。`main()`には未接続で、`print_comparison_table()`と同様に手動で呼ぶ用途。

- **依存**: `playwright`(`venv/`に導入済み)。中核機能(`requests`のみ)とは別の追加依存であり、**別PCで環境構築する場合は`pip install playwright`に加えて`playwright install chromium`(ブラウザバイナリ取得)を忘れずに実行すること**。これを忘れると`fetch_jma_weather_map()`実行時にブラウザ起動でエラーになる。
- **仕組み**: 気象庁のページはJSが天気図を`<img src="data/png/<タイムスタンプ付きファイル名>">`として動的に描画するため、素のHTTPリクエストでは今日の天気図が取得できない(固定URLの静的画像ではない)。そのため`requests`ではなくPlaywright(ヘッドレスChromium)でページを開き、天気図の`<img>`要素の読み込み完了(`el.complete && el.naturalWidth > 0`)を待ってから、その要素だけを`element.screenshot()`で切り出す。ページ全体ではなく要素単体を撮るため、メニュー・サイドバー・広告は最初から一切写り込まない(2026-09確認時点で天気図は600x581pxのネイティブ解像度)。
- **デフォルト表示**: ページを開いた時点で既に「実況」天気図が表示されているため、タブ切り替え操作は不要(2026-09確認時点)。
- **予想天気図(+24h/+48h)の取得(`fetch_jma_weather_map(include_forecast=True)`、2026-09追加)**: ユーザーから「ページ右上の▶ボタンで将来分の天気図を見られるのでは」と指摘を受け、実際にPlaywrightでボタンを押して検証したところ、その通りだった。
  - ページ右上の「ひとつ後の時間を表示」ボタン(セレクタ`img[title='ひとつ後の時間を表示']` — 座標クリックではなくtitle属性で特定。同じ並びに「ひとつ前の時間を表示」「動画再生」ボタンもあるため、位置ではなく属性で区別する必要がある)を押すと、実況→**翌日09時の予想(24時間予想図)**→**翌々日09時の予想(48時間予想図)**の順に切り替わり、3回目のクリックでは変化しない(=それ以上先は無い)ことを実測で確認。これは気象庁の一般公開ページが提供する標準的な予想天気図(FSAS24/FSAS48相当、固定で09時JST)であり、14日先まで見られるような拡張予報ではない。
  - `include_forecast=True`にすると、実況キャプチャと**同一のブラウザセッション内で**連続してボタンを押し、+24h・+48hの画像も追加取得する(サイトへの再アクセスは発生しないため、「1回の診断につき1回程度の取得」という節度あるアクセス方針には抵触しない、という判断)。デフォルト(`include_forecast=False`)は従来通り実況のみ・戻り値も文字列のまま(後方互換)。`True`のときは`[実況, +24h, +48h]`のパスのリストを返す。
  - **活用イメージ**: MSMの実質的な予報範囲(~39時間)は、ちょうどこの実況+24h+48hの3枚でほぼカバーされる。ヤマビヨリの近傍日(MSM区間)の点予報を、気象庁自身の予想天気図と直接見比べる裏付け材料として使える。
- **保存先・ファイル名**: `screenshots/jma_weathermap_<YYYY-MM-DD>_<HHMM>.png`(取得時刻はローカル時刻)。予想天気図は同じタイムスタンプに`_plus24h`/`_plus48h`を付けたファイル名(例: `jma_weathermap_2026-09-02_0007_plus24h.png`)。
- **利用規約**: 気象庁サイトに`robots.txt`は存在せず(404)、利用規約ページ(https://www.jma.go.jp/jma/kishou/info/coment.html )にも自動アクセス自体を禁じる記載はない(2026-09確認)。ただしコンテンツ利用時は「公共データ利用規約(第1.0版)」に基づき**出典表記(例: 出典:気象庁ホームページ https://www.jma.go.jp/bosai/weather_map/ )が必要**。また気象業務法第17条・第23条により、この天気図を元にした独自予報・警報をあたかも気象庁発表であるかのように見せる利用は禁止されている(ヤマビヨリの通常利用 = 個人の登山判断の参考にする範囲では問題にならない想定)。
- **運用ルール(節度を持ったアクセス)**: 気象庁の本番サイトに毎回ブラウザで直接アクセスする機能なので、Open-Meteo側のような3時間キャッシュ層は今のところ持たせていない。**1回の診断につき1回程度の取得にとどめ、ループ処理や短時間の連続呼び出しはしないこと**(自動リトライで無限に叩き直すような実装もしないこと)。頻繁な取得が必要になった場合は、まずキャッシュ層(取得済みファイルの再利用)を検討すること。

## 診断モードの標準フロー(天気図読解つき、2026-09追加)

診断モードでユーザーに1つの山の天気を答えるときは、以下の2段階を基本の流れとする。ステップ1(点予報)は常に実行し、ステップ2(天気図読解)は下記の判断基準に沿って**必要な場合だけ**行う(=毎回無条件に取得するわけではない。2026-09当初は「毎回取得」としていたが、気象庁サイトへの節度あるアクセス運用ルールおよび「点予報だけで明快な日にまで天気図を挟むと冗長」という判断から、条件付き取得に変更)。

1. **点予報の取得・表示**: 既存の`print_day_score_table()`/`print_hourly_table()`をそのまま実行(コード変更不要)。
2. **天気図読解による補足コメント(条件付き)**: 下記のいずれかに該当する場合、`fetch_jma_weather_map()`で気象庁の実況天気図を取得し、Claude Code自身がその画像をReadツールで読み取って、点予報を補足する短いコメントを生成しユーザーに提示する。

   **取得する条件**(いずれか1つでも該当すれば取得):
   - ユーザーが明示的に「天気図も見て」「なぜこの予報なのか」のように理由・根拠を求めた場合(この場合はスコアの値によらず**必ず**取得する)。
   - 対象日の稜線帯スコアが、点予報だけでは判断に迷う範囲にある(目安: 90以上でも30以下でもない=極端に良い/悪いと言い切れない中間帯)。
   - 予報期間中で日によってスコアの変動が大きい(例: 隣接日で20点以上動く、好天と荒天が交互に来るなど)。
   - AM降水確率が40〜60%程度の境界域にあり、「登れる/登れない」の判断が微妙な場合。
   - 地上と上空(1000/2000/3000m帯)で雲量の傾向が食い違う場合(雲海パターン等。`print_hourly_table`の「雲量地上%」と「雲量約○○m%」列を見比べて、地上が高く上空が低い/逆、のように傾向が反転しているケース)。

   **取得を省略してよい条件**: 稜線帯スコアが90以上(明快に好条件)、または30以下(明快に厳しい)で、かつユーザーから理由説明の要求も無い場合。この場合は点予報のみで簡潔に回答してよい。

   - `fetch_jma_weather_map()`は引き続き`main()`には接続しない(手動呼び出しのまま)。理由: 気象庁の本番サイトへの節度あるアクセス運用ルール(前セクション)と、detail.pyの対話フロー(同じセッションで複数の山を選び直すことがある)を踏まえ、**「実際にユーザーへ診断結果を答える」タイミングでのみ1回呼ぶ**運用とする(=コード側で毎回自動取得はしない)。
   - 生成するコメントは、次の3点を最低限含める:
     a. 対象の山が、天気図上のどの気圧系(高気圧/低気圧/前線/熱帯低気圧)の影響下にあるか。
     b. なぜ点予報がその数値になっているのか、広域の気圧配置から説明する一言(例:「高気圧の中心に近く、下降気流のため雲が少ない」「弱い低気圧・前線が近くを通過中で、午後にかけて雲が急速に増えている」等)。
     c. 天気図から読み取れる、点予報の14日先には表れにくい中期的な懸念(接近中の低気圧・熱帯低気圧・前線の動きなど)があれば言及する。無ければ「特段の懸念なし」で良い。
   - 山の緯度経度(`MOUNTAINS`の`lat`/`lon`)から天気図上のおおよその位置を判断すること。天気図の記号の読み方(高/低/熱低/前線の種類/「ゆっくり」等の移動速度表記)と、山の位置の当たり方(経緯度からの近似座標変換)は `references/weather_map_reading.md` を参照。
   - **過信しないこと**: これは目視による定性的な補足であり、点予報の数値を置き換えるものではない。断定的な進路予測などはせず、「〜と考えられる」程度の確度でコメントする(詳細は同reference参照)。

### 稜線風速スコアが評価窓外の強風ピークを見逃す問題 → 「強風注意」列で解消済み(2026-09)

`mountain_climb_score`の風評価(`wind_penalty`)は**稜線帯滞在時間(`RIDGE_START_HOUR`〜`RIDGE_END_HOUR`、デフォルト8-11時)の平均風速**を見る設計で、これ自体は変更していない(稜線滞在中の体感を評価するという設計思想は妥当なため)。ただし、日光白根山の実例で、てんきとくらすの週間予報が「C」(不適)としていた日にヤマビヨリのスコアが82〜85と高めに出るという食い違いが見つかった。原因は、その日の3013m帯風速が早朝05-06時に23m/s台まで急上昇していた一方、8-11時の評価窓ではすでに弱まっており、**評価窓の外の危険な強風ピークがスコアに一切反映されない**という設計上の見落としだった。実際の登山は早出(`EARLY_START_OFFSET_HOURS`分、日の出前から行動開始)が一般的で、評価窓の外こそ実際に行動する時間帯であることも多いため、安全に直結する問題として修正した。

- **採用した方針(案B)**: スコア自体(稜線帯8-11時平均)は変更せず、別軸として「当日の行動時間帯全体における最大風速」を検出し、それが`WIND_PEAK_WARNING_MS`(15.0m/s、`wind_penalty`が満額減点になる閾値と同じ)以上、かつ稜線帯評価窓の**外**で発生している場合にのみ警告を出す(評価窓内のピークは既にスコアに反映されているため警告不要)。
  - detail.py: `compute_day_scores()`が`day_peak_wind_ms`/`day_peak_wind_hour`/`wind_warning`を算出。検出範囲は`print_hourly_table()`と同じ「日の出+`EARLY_START_OFFSET_HOURS`〜日の入り」。
  - mvp.py: `window_scores_by_day()`の`day_peak`が同様に算出。ただしmvp.pyは日没時刻を取得していないため、検出範囲は「AM開始(日の出+`TRIP_START_OFFSET_HOURS`)〜`PM_END_HOUR`固定時刻」で代用(detail.pyより厳密さは劣るが、既存のAM/稜線帯/PM設計に沿った現実的な妥協)。
  - 両ファイルとも`print_day_score_table()`/`print_ranking_table()`に「強風注意(圏外)」列を追加し、該当時は`wind_peak_warning_cell()`が「⚠HH時n.nm/s」の形式で表示(該当なしは「-」)。
  - `WIND_PEAK_WARNING_MS = 15.0`は新しい判断基準ではなく、既存の`wind_penalty`が満額減点とする閾値の再利用(`wind_penalty`のdocstring参照)。他のスコア用定数と同じく`mountain_weather_core.py`で一度だけ定義され、両ファイルがそこから読み込む。
- **検証**: 日光白根山9/4で早朝05時23.8m/sのピークが「⚠05時23.8m/s」として正しく検知されることを確認(detail.py)。mvp.py側でも実データ上で警告が発火することを確認済み(例: 八ヶ岳(赤岳)等、16時12.2m/s台のピークで発火)。
- **未対応の注意点**: mvp.pyは`MIN_SCORE_THRESHOLD`(デフォルト80)未満の山をランキング表示自体から除外するため、その日のスコアが80未満に転落していると「強風注意」列を見る機会自体がない(=その山はそもそも候補に出てこない)。この場合、危険性はランキング除外という形で別途反映されているため実害は小さいが、「除外されたが強風注意付きだった日」を明示的に拾う仕組みはまだ無い。

### 降水タイミングの不確実性を出力に明記(2026-09)

「既知の精度傾向」セクション記載の通り、2〜3日以降の降水タイミングは他サービスと比べても精度が高いとは言えない(立山9/3-9/4の例で4サービス中2対2に割れた)。この不確実性をユーザーに黙って提示するのではなく、該当条件のときは出力に一言添えるようにした。

- **条件(いずれか)**: 対象日が`PRECIP_TIMING_UNCERTAIN_DAYS_OUT`(3)日以上先、またはAM降水確率が`PRECIP_TIMING_BOUNDARY_LOW`〜`PRECIP_TIMING_BOUNDARY_HIGH`(40〜60%)の境界域。
- **表示内容**: `PRECIP_TIMING_NOTE`(「※この先の降水タイミングは日によって変わりやすいため、直前に再確認することをおすすめします。」)を1行追加。
- detail.py: `print_day_score_table()`が全14日分をまとめて表示する構造のため、`precip_timing_note(day_scores)`は**表全体に対して1回だけ**判定し、該当する日が1日でもあれば表の末尾に1行だけ表示する(14日中11日は3日以上先になるため、これは実質ほぼ毎回表示される標準的な注意書きとして機能する)。
- mvp.py: `print_ranking_table(rows)`は日付ごとに個別に呼ばれる構造のため、`precip_timing_note(day_index, rows)`は**呼び出し側(`main()`)がその日のインデックス`i`を渡して日ごとに判定**し、該当すれば各日の表の直後に1行表示する。
- 定数(`PRECIP_TIMING_*`)は他のスコア関連定数と同じく`mountain_weather_core.py`で一度だけ定義され、両ファイルがそこから読み込む。`precip_timing_note()`関数自体は引数の形が2ファイルで異なるため(mvp.py: `day_index, rows`、detail.py: `day_scores`)、統合していない(既知の落とし穴7参照)。

### 「降水量mm(全日)」列の追加(2026-09)

**発端**: 西穂高岳9/5をユーザーがWindy(MSM、meteogram表示)と突き合わせたところ、Windyは日別降水量86.7mmを表示していたのに対し、ヤマビヨリの表は「降水確率%(登り)」列が49.7%だけで、一見「まあまあ」に見えてしまった。実際にヤマビヨリ側の生データを全時間帯で合計すると114.2mm(Windyとほぼ同オーダーで一致)あり、**AM(登り区間)だけを見るスコア設計のせいで、午後〜夜にかけての大雨が表からは見えていなかった**ことが判明。ユーザーからの「次回繰り返さないよう仕様変更したほうがよいのでは」という指摘を受けて対応。

- **対応方針**: `mountain_climb_score`自体(AM降水確率重視の設計)は変更しない。判断基準: 「強風注意(圏外)」列と同じパターンで、**スコアの評価窓の外側で起きているリスクを、スコアとは別の列として同じ表に並べて可視化する**。
- **検討した代替案と却下理由**: 当初「PM窓(12-17時)だけの降水量」を提案したが、実装前に西穂高岳9/5の実データで検証したところ、PM窓(12-17時)の合計は34.3mmで、全日合計114.2mmの3割程度しか捉えられないことが判明(この日は終日ほぼ均等に2〜10mm/hの雨が降り続くパターンで、午後に集中する雨ではなかった)。**PM窓限定では規模を大きく過小評価する**ため、素直に**0-23時の全日合計**を採用した。
- **実装**: `compute_day_scores()`(detail.py)/`window_scores_by_day()`(mvp.py)とも、既存のAM/稜線帯/PM窓の集計とは別に、**時間帯の条件を一切つけずに**その日の`precipitation`(mm/h)を全時間帯合計する`day_precip_by_day`を追加し、結果を`day_total_precip_mm`として返す。`mountain_climb_score`の呼び出し・重みには一切触れていない。
- **表示**: `print_day_score_table()`(detail.py)/`print_ranking_table()`(mvp.py)に「降水量mm(全日)」列を追加。detail.py側は表の下に「AM降水確率が低くても全日ではまとまった雨になる日がある」旨の注記を1行追加(表を1回だけ出す構造のため)。mvp.pyは日付ごとに表を繰り返す構造のため、同じ注記を毎回出すと冗長になるので注記は付けていない(列の見出し自体で意図は伝わる判断)。
- **検証**: 西穂高岳9/1〜9/14で実行し、9/5が114mm(最大)、9/1が0mmと、実際の悪天候日が数値として明確に浮き上がることを確認。mvp.pyでも唐松岳・谷川岳等9/5で44〜46mmと出ることを確認。

## 生JSONキャッシュ層 — mountain_weather_core.py で一元管理(2026-09〜)

`fetch_open_meteo`/`_cache_path`/`_load_cache`/`_save_cache`/`get_with_retry`/`CACHE_DIR`/`CACHE_TTL_SECONDS`/`OPEN_METEO_URL`は`mountain_weather_core.py`に一度だけ定義されており、mvp.py/detail.pyの両方がそこから読み込む(2026-09より前はdetail.py発の設計をmvp.py側に手でコピーしていたが、この移行で統合した)。導入の動機: mvp.pyは75山×3本(jma_msm/ecmwf_ifs025/best_match視程用)のAPIコールをキャッシュ無しで毎回フルに叩いており、実行のたびに数分かかっていた。

- 目的: フォーマット前の生レスポンスをディスクに残し、後から別の変数が必要になったときに全部取り直さず差分だけ取得できるようにする。
- 保存先: `<スクリプトと同じディレクトリ>/cache/{model}_{lat:.4f}_{lon:.4f}_{days}d.json`(例: `jma_msm_36.7514_137.7622_14d.json`)。`model=None` のときは `best_match` 名で保存。`_cache_path()`は`past_days`引数(非0のときだけファイル名に`_past{N}d`サフィックスが付く)も受けるが、mvp.pyはこれを一切使わないので通常のキー(サフィックスなし)のみを生成する。両スクリプトとも同じ`cache/`ディレクトリを見るが、`days`がmvp.py=15・detail.py=14で異なるためファイル名キーが衝突することはない(同じ山を両方のスクリプトで見ても別ファイルになる)。
- TTL: `CACHE_TTL_SECONDS`(3時間)。新鮮かつ要求変数が全部揃っていれば通信なしでキャッシュを返す。新鮮だが変数が足りなければ**その差分だけ**取得してキャッシュJSONにマージ。古い/無い場合は要求分をまるごと取得してキャッシュを作り直す。
- 汎用エントリポイント(core.pyに1つだけ存在。シグネチャ):
  ```python
  fetch_open_meteo(lat, lon, hourly=[...], daily=[...], days=14, model=None, force_refresh=False, past_days=0)
  ```
  Open-Meteoがサポートする**任意の**変数名をそのまま渡せる(そのスクリプトが現在使っていない変数でもOK)。新しい分析軸(積雪など)を試すときはこれを直接呼ぶ。変数名一覧: https://open-meteo.com/en/docs。`past_days`は一回限りの過去日付取得用(detail.py側のユースケース、`scratch_past_date.py`参照)で、mvp.py/detail.pyとも通常の呼び出しでは指定しない(デフォルト0)。
  ```python
  import mountain_weather_core as core
  data = core.fetch_open_meteo(36.7514, 137.7622, hourly=["temperature_2m", "snow_depth"], days=3)
  # または import mountain_weather_detail as m; m.fetch_open_meteo(...) -- detail.pyがcoreから
  # 読み込んだ同じ関数オブジェクトを指す(mvp.py経由でも同様)。
  ```
- `fetch_single_model()`(mvp.py/detail.pyそれぞれに残る、要求変数セットが異なるため)・`fetch_freezing_level()`/`fetch_visibility()`(detail.pyのみ、視程・氷点高度用)はこの `fetch_open_meteo()` の薄いラッパーとして実装されているので、通常のスクリプト実行でも自動的にキャッシュの恩恵を受ける。detail.pyの`fetch_ensemble()`(ECMWFアンサンブル確信度用)は`fetch_open_meteo()`とは別系統だが、`_load_cache`/`_save_cache`/`get_with_retry`/`CACHE_DIR`/`CACHE_TTL_SECONDS`はcore.pyの同じものを再利用している(詳細は該当セクション)。
- `time`モジュールのシャドウイング(既知の落とし穴2参照)は、キャッシュ層自体が`mountain_weather_core.py`内に閉じ込められたことで解消済み — core.py自身が`import time as time_module`で`time_module.time()`/`time_module.sleep()`を使うため、mvp.py/detail.pyのどちらでキャッシュ層を呼んでも同じ実装が動く。mvp.py側にはもうこの層のコード自体が存在しない。
- 同じキャッシュ実行中に得られる予報値は、実行タイミング(モデル更新サイクル、対象日までの日数)によって変わる。**同じ日付でもmvp.pyとdetail.pyを別のタイミングで実行すると数値が食い違うことがあるが、これはバグではなく予報の更新による**(スコア関数自体が同一であることは自明 — 同じcore.py関数を指しているため)。
- **キャッシュサイズの見積もり**: mvp.pyは75山×3モデル=最大225ファイル/15日分。実測でおよそ数MB〜1桁MB程度(1ファイルあたり数KB〜数十KB)。`MOUNTAINS`リストの山数もmvp.py/detail.pyの`days`値も固定なので、同じ山を繰り返し実行してもキャッシュファイルは**上書きされるだけで増え続けない**(キー空間が固定されているため)。肥大化しうるのは (a) `MOUNTAINS`リストに山を追加し続けた場合、(b) `fetch_open_meteo`を一回限りの分析目的で`days`や`past_days`を変えて手動呼び出しした場合(detail.pyの`past_days`使用時など)、の2パターンのみ。日常的な実行では放置してよいレベルだが、気になる場合は`find cache/ -mtime +N -delete`のような手動クリーンアップで十分(自動プルーニングの仕組みはまだ実装していない)。

## 既知の精度傾向(他サービスとの比較、2026-09)

ユーザーが実際にてんきとくらす・Windy・SCW・Mountain-Forecast・WeatherNewsのスクリーンショットを見せながらヤマビヨリ(唐松岳・日光白根山・立山で)の値と突き合わせた際に分かった傾向。**この検証は3山・数日分の非系統的なもの(たまたまユーザーが見せてくれた画面との比較)であり、統計的に厳密な精度評価ではない**点は差し引いて読むこと。

- **強み: 標高を揃えて比較すると、雲量・気温・風速は他サービスと高い精度で一致する。**
  - 雲量: 日光白根山9/1で「地上は曇りだが山頂帯(3013m)は快晴」という雲海パターンをヤマビヨリが検出、後日WeatherNewsの登山口アイコン(曇り)が独立に裏付けた。SCWの雲量予測図(Total Cloud Cover)ともグレー階調が概ね対応。
  - 気温: てんきとくらすの700hPa気温、WeatherNewsの山頂(3015m)時間別気温とも、ヤマビヨリの対応する気圧面の値とほぼ一致(1℃前後の差)。
  - 風速: Mountain-Forecastの山頂(3015m)風速と、ヤマビヨリの稜線風速が同日でほぼ一致(11.1 vs 11.5m/s)。
  - **逆に、標高を揃えずに比較すると大きくズレる**(Windyの「登山口」表示や、モデル地形の平滑化で実際より低い標高を表示するケースなど)。他サービスとの比較時は、相手が「山頂」「登山口」「何m地点」のどれを表示しているか必ず確認すること。
- **過去に見つかり、修正済みの弱点**:
  - 気温推定の温暖バイアス(3〜5℃)。旧`estimate_temp_c()`(氷点高度+標準気温減率)方式の廃止と`temperature_XXXhPa`直接取得への統一で解消(detail.py、mvp.pyは元から直接取得方式だったため対象外)。
  - 稜線帯評価窓(8-11時)外の強風ピークの見逃し。「強風注意」列の新設で解消(両ファイル)。
- **現時点で残る限界**: **2〜3日以降の降水タイミング**(どの日にピークの雨が来るか)の精度は、他サービスと比べて高いとは言えない。立山9/3-9/4の大雨イベントで、ヤマビヨリ・Windy・Mountain-Forecast・WeatherNewsの4サービスが2対2で「どちらの日がピークか」割れた。これはヤマビヨリ固有の弱点というより、この先読み日数(2〜3日先)における数値予報モデル自体の本質的な不確実性による(詳細はSKILL.md「降水タイミングの不確実性」出力機能を参照)。

## 既知の落とし穴

1. **`freezing_level_height` と `visibility` は `jma_msm` / `ecmwf_ifs025` を `models=` 指定すると常にnullで返ってくる。** 取得するには `models` パラメータを付けない(＝Open-Meteoのデフォルト `best_match`)必要がある。detail.pyの`fetch_freezing_level()`/`fetch_visibility()`、mvp.pyの`fetch_forecast()`内の3本目の`fetch_single_model(..., model=None, ...)`呼び出しは、いずれも `model=None` で呼ぶことでこれに対応済み。他の気圧面変数(風速・風向・雲量・湿度・**気温**`temperature_XXXhPa`)は名前付きモデルで問題なく取れる(2026-09、detail.pyで`temperature_XXXhPa`を試したところnullではなく実測相当の値が返ってくることを確認済み — この変数だけ「使えない」と誤って想定し、氷点高度からの推定に頼っていた過去の設計判断が長らく残っていた)。新しい変数を追加するときは、まず named modelで試してnullしか返らないか確認すること(同じ罠に何度もはまっている)。
2. **`time` モジュールのシャドウイング。** `mountain_weather_detail.py` は `from datetime import date, datetime, time, timedelta` を使っているため、素の `import time` を later で書くと `datetime.time` に上書きされ `time.sleep()` が `AttributeError` になる(実際にリトライ処理でこのバグを踏んで修正済み)。このファイルでは `import time as time_module` とし、スリープは `time_module.sleep()` を使うこと。`mountain_weather_mvp.py` は `datetime` から `time` をインポートしていないため、この問題はない(ただし将来 `from datetime import time` を足すと同じ罠にはまる)。
3. **(2026-09に解消) `MOUNTAINS` リストはかつて2ファイルに別々にコピーされていた。** 現在は`mountain_weather_core.py`の単一のリストをmvp.py/detail.pyの両方が`from mountain_weather_core import MOUNTAINS`で読み込むため、山を追加・削除する場合はcore.py側を1回直すだけでよい(2ファイルを揃える必要はもう無い)。ただし**リストの並び順に依存する番号(detail.pyの非対話選択など)は、リストが変わるたびにズレる**点は変わらないので、SKILL.md記載の番号を鵜呑みにせず都度確認すること。
4. **(2026-09に解消) `cache/` はかつて detail.py 実行時のみ生成されていた。** mvp.py にはキャッシュ層が無く、75山×3本のAPIコールを毎回フルで叩いていたため実行に数分かかっていたが、detail.pyのキャッシュ層(`fetch_open_meteo`等)を同一ロジックで移植し(その後2026-09に`mountain_weather_core.py`へさらに統合)解消済み。現在は両ファイルとも`cache/`を使う(詳細は「生JSONキャッシュ層」セクション)。過去の記述を鵜呑みにして「mvp.pyは遅くて当然」と説明しないこと — 2回目以降(3時間以内の再実行)はキャッシュ命中で大幅に高速化される。
5. **(2026-09に解消) スコア式(`mountain_climb_score`と6つのpenalty関数、`wet_chill_adjustment_c`、`SCORE_WEIGHTS`)はかつて2ファイルに同一コードとして手でコピーされていた。** 現在は`mountain_weather_core.py`に一度だけ定義され、両ファイルがそこから読み込むため、調整はcore.py側を直すだけでよく、ファイルごとにスコアが食い違う状態には原理的に戻らない。
6. **`safe_avg`(0.0 if 欠損)と`safe_avg_or_none`(None if 欠損)は使い分けが必要。** wind/cloudのように「0.0=ベナイン(無風/快晴)」な指標には`safe_avg`でよいが、視程のように「0.0=最悪(ホワイトアウト)」な指標に`safe_avg`を使うと、単にその日のデータが無いだけなのに満額ペナルティがつく事故になる。視程には`safe_avg_or_none`を使い、`visibility_penalty(None)`側でペナルティなし(0.0)として扱っている。新しい指標を追加する際は、0/Noneどちらの扱いが安全側かを都度判断すること。
7. **`fmt()`と`wind_peak_warning_cell()`/`precip_timing_note()`は意図的にcore.pyへ統合していない。** `fmt(val, ndigits=0)`はmvp.pyでは`round(val, 0)`(結果は"1234.0"のような文字列)、detail.pyでは`round(val)`(結果は"1234")と、**2ファイルで表示結果が異なる**(2026-09の統合作業で発見した既存の不一致で、統合時に挙動を変えないためあえて残した)。`wind_peak_warning_cell()`はこの`fmt()`に依存し、`precip_timing_note()`は引数の形(mvp.py: `day_index, rows`、detail.py: `day_scores`)が2ファイルで異なるため、いずれも各ファイルに個別定義のまま。数値そのもの(スコア・稜線風速など)は完全に一致するが、**画面表示の小数点/整数表記だけmvp.pyとdetail.pyで微妙に異なる場合がある**ことを覚えておくこと。

## 実行方法

```bash
cd C:\mountain-weather
./venv/Scripts/python.exe -m pip install -r requirements.txt   # 初回セットアップ(中核機能=requestsのみ)
./venv/Scripts/python.exe mountain_weather_detail.py        # 対話的に山を選択
echo "12" | ./venv/Scripts/python.exe mountain_weather_detail.py   # 非対話(12=富士山(剣ヶ峰)、リスト順依存。要事前確認)
./venv/Scripts/python.exe mountain_weather_mvp.py            # 全山ランキング(非対話)
```

`mountain_weather_core.py`は直接実行しない(mvp.py/detail.pyからimportされるだけのモジュール)。

`mountain_weather_mvp.py` 側の主な調整パラメータ: `REGION_FILTER`(空=全地域)、`TOP_N_PER_DAY`(Noneで無制限)、`MIN_SCORE_THRESHOLD`(デフォルト80.0)、`TRIP_START_OFFSET_HOURS`/`TRIP_DURATION_HOURS`(AM/登り)、`RIDGE_START_HOUR`/`RIDGE_END_HOUR`(稜線帯滞在)、`PM_START_HOUR`/`PM_END_HOUR`(下山・対流雷リスク)、`SCORE_WEIGHTS`(6軸の重み)、`CACHE_TTL_SECONDS`(キャッシュ有効期間、デフォルト3時間)。
`mountain_weather_detail.py` 側: `FORECAST_DAYS`(14)、`EARLY_START_OFFSET_HOURS`(表示用テーブルの開始オフセット)、`TRIP_START_OFFSET_HOURS`/`TRIP_DURATION_HOURS`/`RIDGE_START_HOUR`/`RIDGE_END_HOUR`/`PM_START_HOUR`/`PM_END_HOUR`(スコア用の3区間、mvp.pyと同じ意味)、`SCORE_WEIGHTS`、`CACHE_TTL_SECONDS`。

## 出力フォーマット

- **mvp.py**: 登山向け総合スコアと、雷リスク(CAPE)・稜線風速・稜線雲量・稜線視程(m)・降水確率・体感温度を表形式で提示する。
- **detail.py**: 同じ列構成の日別総合スコア表(`print_day_score_table`、稜線視程(m)列を含む)に加え、1時間ごとに地上+1000m/2000m/3000mの4バンド分の雲量・風速風向を並べた表(`print_hourly_table`)を続けて提示する。`print_hourly_table`/`print_comparison_table`側には視程列は追加していない(スコアに使う日別サマリー表のみ対応)。
- どちらも最後に「行動可否」の総評と、防風・防寒などの注意点を一言でまとめる。
