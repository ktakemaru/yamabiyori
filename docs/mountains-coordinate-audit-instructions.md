## 0. 目的と背景
展望図の実証(段階2・2.5)で、ヤマビヨリ本体の `MOUNTAINS` の座標が、山頂から大きく離れている山が見つかった。

## 3. 調べること(全 76 座)
材料は、手元にあるものだけ: `MOUNTAINS`、国土地理院 1003 山の保存済みデータ(`cache/panorama/gsi_1003/`)、段階2 の辞書、段階2.1 の OSM の保存済み応答(`cache/panorama/osm/`。展望地だけ。山頂の点は `natural=peak` も付いた展望地に限られる)、手元の標高タイル。

山ごとに次を出す。
1. `MOUNTAINS` の id・name・緯度経度・標高(持っていれば)。
2. **同じ名前の 1003 山の点**: 距離の上限なしで、名前で探す(段階1 の対応は 3km 以内しか見ていなかったため、唐松岳を見落とした)。
   - 名前の照らし方: `MOUNTAINS` の name から括弧の補足を外したもの、括弧の中の名前、段階2 の辞書の呼び名。同じ名前の点が複数あるときは、いちばん近い点と、その距離。50km を超えるものは「同名の別の山」として候補から外し、その旨を書く。
   - 見つかったら: 距離(m)・方位・1003 山の標高・`MOUNTAINS` の標高との差。
3. **座標のいちばん近くにある 1003 山の点**(名前を問わない): 名前・距離。**それが 2 の山と違う名前で、2 の山より近いときは「別の山の近く」の印**を付ける(唐松岳の形)。

5. 1003 山に同じ名前の点が無い山: OSM の保存済み応答に `natural=peak` の付いた点が 300m 以内にあれば、名前・距離・方位(石割山の形)。無ければ「照らす相手なし」。
6. 区分(読みやすさのため): 山頂の点までの距離が 100m 未満 / 100〜300m / 300m〜1km / 1〜3km / 3km 以上 / 照らす相手なし。

## 4. 天気の計算への影響(通信あり・少量)
目的は、「座標のずれで、予報の格子(計算に使われる地点)が変わるか」を確かめること。
1. まず本体のコードを**読んで**、`MOUNTAINS` の座標と標高が天気の取得でどう使われているかをまとめる(どの関数が、緯度経度・標高をどの API のどの引数に渡すか。標高の補正の有無)。コードは変えない。
2. 山頂の点までの距離が **300m 以上**の山と「別の山の近く」の印が付いた山について、Open-Meteo の予報 API に、今の座標と 1003 山の山頂の点の 2 通りで問い合わせ、**応答の格子の緯度経度・標高(`latitude`・`longitude`・`elevation`)**を比べる。
   - 本体と同じ API・同じモデルの指定・同じ標高の渡し方で行う(1 の調べのとおり)。取る変数は 1 つ(気温)、期間は 1 日だけにして、通信を軽くする。
   - 本体の通信の部品(通信間隔の調整・429 の種類分け)を**呼び出して**使えるなら使う。使えなければ、1 回ごとに 2 秒以上あける。
   - 上限: **合計 60 回**。対象が多くて超えるときは、距離の大きい順に行い、残りは「未確認」。
   - 429 が出たら、本体の決まりどおりに待つ。`daily`・`hourly` の上限に当たったら、そこでやめて報告する。
3. 山ごとに: 格子が同じか・違うか、違うなら格子どうしの距離と標高の差。その日の気温の差(参考。1 日ぶんの最大の差)。
4. Open-Meteo 以外には通信しない(国土地理院・OSM・Wikipedia・検索もしない)。通信の回数・時刻・HTTP の状態を `cache/panorama/audit/ledger.json` に記録する。
