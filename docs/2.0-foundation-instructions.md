## 第 2 部: Open-Meteo の利用上限への対応(ブランチ `feature/open-meteo-pacing`。`git switch main` → `git switch -c feature/open-meteo-pacing`)

### 8. 今の状態と、直す理由

- 通信は `mountain_weather_core.py` の `get_with_retry` を通る。失敗すると 2 秒・4 秒待って 3 回試し、だめならその山を「取得失敗のためスキップ」して次の山へ進む。429(利用上限)も、ほかの通信エラーと同じ扱い。
- 問題 1: 1 分の上限に当たったとき、2 秒・4 秒の待ちでは戻らず、山が次々に飛ばされる。
- 問題 2: 1 時間・1 日の上限に当たったとき、回復しないのに、残りの山すべてで 3 回ずつ通信を続ける(無駄な通信が 200 回以上になりうる)。
- 問題 3: 429 の理由(1 分・1 時間・1 日)が画面に出ない。
- 問題 4: 探索モードは 76 座で通信が続き、1 分あたりの利用量が上限(600)に近い。接続の使い回し(v1.9.1)で速くなった分、間をあけずに通信するようになった。

手本: ホシビヨリ v1.1.0 が同じ対応を入れている。`C:/hoshibiyori/step5_cloud_forecast/cloud_forecast.py`(429 の種類分け・65 秒待ち・通信の重さの見積もり・間隔の調整)と、`C:/hoshibiyori/CHANGELOG.md` の 1.1.0 の項、`C:/hoshibiyori/tests/test_open_meteo_pacing.py` を**読んで、考え方を写す。コードを import しない・ファイルをコピーしない**(ヤマビヨリの中に、ヤマビヨリの書き方で書く)。

### 9. 作るもの(1): 429 の種類分け

- 429 のとき、応答の本文(JSON の `reason`。JSON でなければ本文の先頭 200 文字)を読み、`minutely`(1 分)・`hourly`(1 時間)・`daily`(1 日)・`unknown` に分ける。分け方はホシビヨリの実装に合わせる。
- 種類と理由を、画面に 1 行出す。
- `minutely`: 「1分の上限のため65秒待ちます(n/5)」と出して 65 秒待ち、**同じ通信を取り直す**。1 回の実行で合計 5 回まで。6 回目は下の「中止」と同じ扱い。
- `hourly`・`daily`・`unknown`: その通信を失敗にし、**「利用上限に達した」ことを呼び出し元に伝える専用の例外**を上げる(名前は自由。`requests.exceptions.RequestException` を継がせるかは、既存の `except` の書き方を読んで、既存の動きを壊さないほうを選ぶ)。この場合、2 秒・4 秒の再試行はしない。
- 429 以外のエラー(接続エラー・408・5xx など)の再試行(回数・待ち・打ち切り)は変えない。

### 10. 作るもの(2): 利用上限に達したら、残りの山を取りに行かない

- 探索モード(`mountain_weather_mvp.py`)で、上の専用の例外が出たら、**残りの山の取得をやめる**。すでに取れた山だけで、今までどおり結果を出す。
- 取れなかった山の扱い(表示・`--json-out` の `pool_size`・`fetched` の数え方)は、今の「取得失敗のためスキップ」と同じ形にそろえる(コンシェルが `fetched` < `pool_size` を見ているため、数え方を変えない)。
- 画面に 1 回だけ、「利用上限(種類・理由)のため、残り N 座の取得をやめました」と出す。
- **終了コードの意味は変えない。** 今、一部の山が取れなかったときの終了コードを先にコードで確かめ、それと同じにする。確かめた結果を報告書に書く。
- 診断モード(`mountain_weather_detail.py`)は、1 つの山を取るだけなので、9 章の「種類を画面に出す」「1 分の上限なら 65 秒待つ」だけが効けばよい。それ以外の動きは変えない。ENS(`ensemble-api.open-meteo.com`)とひまわり・天気図の取得も同じ関数を通るなら、9 章の扱いが同じように効く(ひまわり・気象庁の 429 は Open-Meteo の理由の形ではないので、`unknown` になる。今の動きより悪くならないことをテストで確かめる)。

### 11. 作るもの(3): 探索モードの通信の間隔の調整と、時間の内訳

- **探索モードだけ**で有効にする(診断モードでは無効。診断モードの待ち時間を増やさないため)。`mountain_weather_core.py` に仕組みを置き、`mountain_weather_mvp.py` の `main()` が有効にする形にする。既定は無効。
- 対象は `api.open-meteo.com` への通信だけ。
- 1 回の通信の重さを `max(1, 変数の数/10) × max(1, 予報日数/14)` と見積もる(ホシビヨリと同じ式。**式と数字を変えない**)。直近 60 秒の重さの合計が **300**(1 分の上限 600 の半分。ホシビヨリの `PACING_LIMIT_PER_MINUTE` と同じ値)を超えないよう、通信の前(再試行も含む)に必要なだけ待つ。キャッシュから読んだ分は数えない。
- 定数の名前は自由だが、値(300・65 秒・5 回)は 1 か所にまとめ、コメントに「ホシビヨリ v1.1.0 と同じ値。2026-11-13 の実測にもとづく安全側の設定」と書く。
- 待ちが起きたときだけ、その旨が分かる表示を出す(待ちが無い実行の途中の表示は、今までと同じにする)。
- **探索モードの最後に、時間の内訳を 1 行足す**: 全体の秒数 / Open-Meteo の通信 / 間隔の調整 / それ以外(例は、ホシビヨリの「実行時間の内訳: …」の行)。これは既定の画面の出力が 1 行増える変更で、利用者が承認している。
  - ただし、既存のテストが画面の出力を丸ごと比べていて、この 1 行で落ちる場合は、**期待値を書き換えず**、この行を標準エラー出力に出す形にして、報告書に書く。
- 時計と待ち(`time`・`sleep`)は、テストで差し替えられる作りにする(テストで本当に待たない)。

### 12. 第 2 部のテスト・受け入れ条件・文書

テスト(通信しない・待たない。`requests` と時計をモックする):

1. 429・`reason` が 1 分の上限 → 65 秒待って取り直し、成功する。待ちの回数が数えられる。
2. 1 分の上限が 6 回続く → 5 回待ったあと、専用の例外。
3. 429・1 時間の上限、1 日の上限、理由が読めない → 待たずに専用の例外。2 秒・4 秒の再試行をしない。
4. 探索モードで、途中の山で専用の例外 → 残りの山に通信しない(通信の回数を数えて確かめる)。取れた山の結果は出る。`pool_size`・`fetched` が今の決まりどおり。
5. 間隔の調整: 重さの合計が 300 を超える並びで、待ちが入る。超えない並びでは待たない。キャッシュから読んだ分は数えない。診断モードでは待たない。
6. 接続エラー・5xx の再試行が、今までと同じ(既存のテストがそのまま通る)。
7. 429 でない通常の成功の経路で、通信の回数・引数・戻り値が今までと同じ。

## 14. 報告書の形(短く)

各部の報告書と、会話の最終メッセージに、同じ要点を書く。

1. **結果**: 完了 / 一部完了 / 止めた(どの条件か)
2. **できたこと**(変えたファイルと、1 行ずつの説明)
3. **テストの結果**: 変更前と変更後の最後の行
4. **確かめたこと**(受け入れ条件ごとに、どう確かめたか)
5. **未確認のこと**(実通信で確かめていないことを、必ずここに書く。とくに第 2 部は、本物の 429 では確かめていない)
6. **コンシェル側・ほかのビヨリへの申し送り**
7. **利用者がやること**(1 ステップずつ。どのウィンドウで何を打つか、成功の見分け方)
   - push の手順(2 つのブランチ)。コマンドは Claude Code の中で `!` を付けて打つ形と、パスを `/` で書くことを明記する。
   - 実通信での確かめ: 探索モードを `--limit 3` で 1 回、そのあと全座で 1 回(`--json-out C:/temp/yama-explore.json` つき)。成功の見分け方(最後に時間の内訳の行が出る・JSON の各山に `id` がある)。
   - 2 つ目の PR のマージで `CHANGELOG.md` の衝突が出るかどうかは、`git merge-tree` で確かめてから書く(推測で書かない)。
8. **利用者に決めてほしいこと**

実行していない確認を「確認済み」と書かない。テストを実行していないなら、完了と言わない。
