## 2. 今回の変更で変わったか

- **名前・引数・戻り値の形**: 上の表の名前は、どちらのブランチでも変えていない(`git diff main` で確かめた。第 1 部は `MOUNTAINS` への `id` の追加と `mountain_by_id` の追加、第 2 部は `get_with_retry` の 429 の扱いと新しい名前の追加だけ)。`compute_ensemble_confidence_by_day`・`fetch_ensemble`・`nearest_pressure_level`・標高補間・較正の関数は差分に無い。
- **`MOUNTAINS` の各山の項目**: 名前・座標・標高・地域・アクセスは不変(第 1 部の報告書 A2)。増えるのは `"id"` だけ。
  - `id` が増えて困る使い方(dict の丸ごとの比較、項目の数の決め打ち、`**m` の展開)は見つからなかった。山名で引いて `lat`・`lon`・`elevation_m` を読むだけ。
  - 影響は 1 点だけ: `plugin_confidence_snapshot.py` が山の dict をそのまま envelope の `"mountain"` に保存するので、**マージ後のスナップショットには `"id": "m0NN"` が 1 つ増えて入る**。`confidence_by_hash.py` はそこから `lat`・`lon` を読むだけなので困らない。
- **版の記録**: 本体の `mountain_weather_core.py`(両ブランチ)と `mountain_weather_detail.py`(第 1 部)の sha256 と git hash が変わる。マージ後の `plugin_confidence` スナップショットは、確信度の出力が変わらなくても**新しい版として記録される**(`confidence_by_hash summary` で別の版に見える)。確信度の計算の行は変えていないので、`confidence_by_hash crosshash`/`recompute` で比べれば同じ値になるはず(実行はしていない)。

## 3. 第 2 部の変更(429 の扱い・間隔の調整)とのぶつかり

- バックテスト基盤は、Open-Meteo への通信を**自前の `requests.Session` と自前の 429 の扱い**(`collect_ensemble.get_with_rate_limit_retry`: 429 なら 65 秒待って再試行)で行う。系統3b は本体の `detail.fetch_ensemble` を自前の関数に差し替えてから `compute_ensemble_confidence_by_day` を呼ぶので、**本体の `get_with_retry` を通らない**。そのため本体の 429 の種類分け・65 秒待ち・`OpenMeteoRateLimitError` は、バックテスト基盤の通信には効かない(ぶつからない)。
- 本体の通信の間隔の調整は**既定で無効**で、有効にするのは探索モードの `mountain_weather_mvp.main()` だけ。バックテスト基盤は `mountain_weather_mvp` を import していないので、間隔の調整は効かない。
- 本体の `_RUN_STATS`(1 回の実行の記録)は、`mountain_weather_core` を import しただけでは何も通信せず、待ちもしない。
