`mountain_weather_core.py` の中身:
- **429 の種類分け**: `classify_rate_limit(reason)`(大文字小文字を区別せず daily → hourly → minutely の順に語を探す。どれも無ければ `unknown`。ホシビヨリと同じ分け方)、`rate_limit_reason(resp)`(JSON の `reason`、読めなければ本文の先頭 200 文字)。画面に「(ホスト名 が429(利用上限、種類=…)を返しました。reason: …)」の 1 行。
- **minutely**: 「1分の上限のため65秒待ちます(n/5)」と出して 65 秒待ち、同じ通信を取り直す。1 回の実行で合計 5 回まで(`configure_open_meteo_pacing()` で 0 に戻る)。2 秒・4 秒の再試行の回数は使わない。6 回目は下と同じ扱い。
- **hourly・daily・unknown(と、使い切った minutely)**: 再試行せず `OpenMeteoRateLimitError` を上げる。**`requests.exceptions.RequestException` を継がせた**。理由: 既存の呼び出し元(診断モードの `main_single_mountain`・ENS の確信度・ひまわりのモザイク・探索モード)はすべて `except requests.exceptions.RequestException` で受けており、継がせれば今の「取得失敗」の動き(診断モードの終了コード 2、ENS の注記、ひまわりの灰色タイル)がそのまま続くため。探索モードだけが先にこの例外を受ける。
- **429 以外**(接続エラー・408・5xx・`raise_for_status` の HTTPError)の再試行(3 回、2 秒・4 秒、最後の例外を上げる)・打ち切り 20 秒・`session.get` の引数(`params`・`timeout` だけ)は変えていない。429 のときだけ `raise_for_status` を呼ばない。
- **通信の間隔の調整**(`RequestPacer`): 重さ `max(1, 変数の数/10) × max(1, 予報日数/14)`(ホシビヨリと同じ式)。**変数の数は hourly と daily の合計で数えた**(安全側。ホシビヨリは hourly だけの通信なので差が出ない)。予報日数は `forecast_days`(無ければ Open-Meteo の既定の 7)。直近 60 秒の合計が 300 を超えないよう、通信の前(再試行・取り直しも含む)に待つ。対象は `api.open-meteo.com` だけ(ENS の `ensemble-api.open-meteo.com`・気象庁は対象外)。既定は無効で、探索モードの `main()` だけが有効にする。キャッシュから読んだ分は `get_with_retry` を通らないので数えない。待ちが起きたときだけ、最初の 1 回に「(Open-Meteo の利用上限を避けるため、通信の間隔を調整しています。待った秒数は最後に出します)」を出す。
- 値(300・60 秒・65 秒・5 回)は 1 か所(`PACING_LIMIT_PER_MINUTE` ほか)にまとめ、「ホシビヨリ v1.1.0 と同じ値。2026-11-13 の実測にもとづく安全側の設定」とコメントした。
- 時計と待ちは `core._clock()`・`core._sleep()`(呼ぶたびにモジュールの名前を引く)で、テストで差し替える。2 秒・4 秒の待ちは従来どおり `time_module.sleep`(既存テストが差し替えている)。
- **内訳の行**: `timing_breakdown_line()`。例「実行時間の内訳: 全体 150.0 秒 / Open-Meteoの通信 100.0 秒 / 間隔の調整 20.0 秒 / それ以外 30.0 秒(全体 − 通信 − 間隔の調整)」。65 秒待ちがあれば「間隔の調整 85.0 秒(うち1分の上限の待ち 1 回・65.0 秒)」。「Open-Meteoの通信」は open-meteo.com への `session.get` の時間(2 秒・4 秒の待ちを含み、間隔の調整と 65 秒待ちは含まない)。「全体」は `run_ranking()` の始まりから(import の時間は含まない)。

`mountain_weather_mvp.py` の中身:
- 利用上限の例外を受けた山は、従来どおり「(山名: 取得失敗のためスキップ - HTTP 429(利用上限、種類=…、reason=…))」と出し、続けて 1 回だけ「(利用上限(種類=…、reason=…)のため、残り N 座の取得をやめました)」と出して、ループを抜ける。**N はその山を含まない、まだ取りに行っていない山の数**。

- ループの本体の字下げは変えていない(第 1 部とのマージの衝突を避けるため)。

## 5. 未確認のこと

- **本物の 429 では確かめていない**(実通信をしない指示のため)。とくに、Open-Meteo が実際に返す 429 の本文の形(`reason` の文言)は、ホシビヨリの記録(`Minutely API request limit exceeded. Please try again in one minute.` など)に合わせたテストでしか確かめていない。
- **探索モードの所要時間は実測していない**。見積もりの重さ約 1,221 を 1 分 300 で送ると、最初の 300 は待たずに送れ、残り約 921 に約 3 分かかるので、**全山で今の約 137 秒から約 4〜5 分に延びる見込み**(キャッシュが効いている分は短くなる)。
- 見積もりでは、全山の探索 1 回で約 1,221。1 時間の上限 5,000 には 1 時間に約 4 回、1 日の上限 10,000 には 1 日に約 8 回で届く(同じ IP のほかのビヨリ・コンシェルの通信は含まない)。重さの数え方は Open-Meteo の実装と同じかどうか確かめていない(ホシビヨリと同じ式を使っただけ)。
- 診断モードで 1 分の上限に当たったときに 65 秒待つ動きは、テスト(`get_with_retry` 単体)でしか確かめていない。
- バックテスト基盤との関係は `docs/2.0-backtest-compat-notes.md`(一部のテストは未確認)。
